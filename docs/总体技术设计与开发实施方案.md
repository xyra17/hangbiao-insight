日期：2026-09-21。状态：用户已确认 Django／DRF、PostgreSQL、Celery／Redis、LangGraph、React／TypeScript／Ant Design 主体架构迁移。自主调查及受控内部写入范围已确认；具体供应商、生产环境与完整工程验证仍按阶段完成。

本文把 V2 需求转成可开发、可验收的系统设计，覆盖数据接入、指标计算、证据追溯和运营处理。采用模块化单体，业务接口与后台任务分进程运行，以关系数据库保存业务事实及版本。标准检查使用 Python 固定流程，自主调查使用 LangGraph，Celery 负责后台投递与执行，PostgreSQL 保存业务事实及图检查点；不采用 LangChain create_agent 上层循环。一次交付需求范围内的完整产品，工作包仅表示开发依赖，不表示分批产品版本。

## 1 设计边界与待确认条件

用户已确认采用单台云服务器，供 3–10 人通过浏览器使用，最多管理 1,000 个子 ASIN；本次保持报表导入并预留 API 接入扩展点。当前业务基线采用文件导入，不包含 Amazon API 自动同步、外部消息推送、ERP 写回或自动修改商品。系统可以提出核查建议、分派内部任务、导出报告，由运营在外部平台执行并回填结果。新增 API 同步应先确认授权、数据范围和验收变化，不能仅凭保留接口认定已经支持。

按已确认规模，将需求中的对象容量从 100 个调整为最多 1,000 个子 ASIN，覆盖 3–10 名用户；保留 180 天数据、至少 10 万条反馈及交易记录、8 核 16 GB SSD 的验收配置，已有标注数据的一轮扫描不超过 15 分钟，缓存读取 P95 不超过 3 秒。SKU 展开后的分析对象数另行记录，不把 1,000 个 ASIN 当成最多 1,000 个 SKU。验收还需加入 10 名用户并发访问、100 万条记录的压力档位和首次批量标注测量；压力档位用于发现容量边界，正式支持的数据量与标注时限在真实报表规模和模型吞吐验证后确认，不能仅凭 ASIN 数保证性能。

部署位置、人数、ASIN 上限和报表导入范围已经确认。上线前仍需确认模型服务与数据传输区域、实际 SKU 及记录规模、原始报表字段和覆盖范围。前两项影响容量及模型选型，最后一项通过样本契约验证解决。没有真实字段时明确缺口，不把预期字段写成平台保证。

## 2 总体结构与模块职责

业务主链为：文件接入 → 数据质量及映射审核 → 发布数据版本 → 指标与语义计算 → 异常及证据 → 报告 → 运营动作 → 到期复查。每个箭头都有任务状态、输入版本和错误记录；页面请求不串行等待整条链完成。

| 模块 | 负责的内容 | 对外产物 |
|---|---|---|
| 身份与商品 | 用户、店铺权限、商品及历史映射、负责人 | 授权范围、稳定分析对象 ID |
| 数据接入 | 来源契约、文件、解析、预览、隔离、发布 | 数据修订版、覆盖清单、导入错误 |
| 指标与检测 | 时间窗、分子分母、统计检验、规则触发 | 指标快照、检测结果、规则版本 |
| 语义与检索 | 中英文标注、安全线索、原文检索 | 带原文位置的标签与检索结果 |
| 证据与报告 | 事实、缺口、候选排序、表达校验 | 不可变报告版本及引用关系 |
| 运营处理 | 事件聚合、指派、动作、复查、关闭 | 当前事件状态、处理历史、站内提醒 |
| 任务与运行 | 调度、重试、审计、导出、备份 | 任务台账、运行状态、恢复记录 |

这些是同一后端中的明确业务边界，不拆成独立微服务。只有所属模块能写入其业务表，其他模块通过服务接口读取或提交命令。采用同一数据库便于把发布、审计和任务投递记录放在同一事务中。

部署由浏览器、同源 Web 入口、业务 API、后台工作进程、单实例调度器、关系数据库、任务消息组件和文件持久存储组成。Web 与工作进程共用领域逻辑，工作进程不能绕过权限或自行改变业务口径。数据库是业务状态依据，消息队列和缓存均可重建。

## 3 数据怎么进来

### 3.1 来源契约先于导入适配器

每一种报表有独立契约，至少包含来源、报表类型、店铺站点、原生粒度、字段及类型、业务主键、时区、币种、税费口径、日期含义、覆盖范围、全量快照或增量语义、修订规则和映射版本。契约附一份脱敏真实样本与字段解释，测试样本不能证明实际平台一定提供该字段。

日销售流量、订单发货、退款、退货、库存可售、评论、页面星级、经营事件分别建契约。辅助来源可缺失，但必须显示缺口及影响。单独导入百分比而没有分子分母，只能展示该来源的值；无法还原历史状态的库存快照不回填历史可售天数。

同一业务字段存在 Amazon 和 ERP 等多个来源时，配置按店铺、对象、日期及指标生效的权威来源规则。不直接相加重复业务数据；冲突保留差异供核查。更换权威来源生成配置版本并触发受影响范围重算。

API 扩展点统一为 SourceAdapter：描述契约、发现批次、产出原始资料及覆盖清单。文件适配器本次实现；未来 API 适配器同样走暂存、校验、发布和版本追溯，不另写一套计算。预留接口不包括凭据授权、限流重试、自动同步或平台数据可得性的交付承诺。云服务器目录导入指服务器上已授权目录或挂载目录，浏览器不会自动读取运营电脑文件夹；个人电脑文件通过上传接入。

### 3.2 导入发布流程

- 接收：上传 CSV 或从已授权目录接收稳定文件。目录监听只读；连续两次检查大小及修改时间稳定后才读取，不处理正在写入的文件。限制大小、编码、列数与路径范围，禁止任意服务器路径读取。
- 固化：计算文件哈希，保存不可变原始文件和来源元数据。客户端提供的哈希仅供参考，以服务端计算为准。同来源及授权范围内重复文件返回原批次，不创建重复事实。
- 解析：按契约分块解析到暂存区，保留原始行号、原始值、标准化值、错误码。解析进度支持中断续跑。
- 校验：检查主键、数据类型、时间范围、对象映射、重复冲突及覆盖声明；展示预计新增、修订、重复、隔离数量和受影响日期。
- 确认：首次来源或映射变更必须预览确认。已确认契约的后续目录文件可自动发布；未知列含义、粒度变化或严重质量错误进入待处理状态。
- 发布：按来源、授权范围和覆盖分区，在事务内激活通过验证的修订、写入覆盖清单及任务投递记录。整批严重错误不发布；允许的行级隔离必须把受影响分区标成 partial，不能保留完整标记。
- 后处理：异步计算指标、标注新增文本、刷新事件。用户可离开页面，任务状态独立保存。

发布失败不能出现一半新数据与一半旧数据被计算的情况。原始文件先写入并校验成功，再提交数据库引用；未被引用的临时文件定期清理。文件写入与数据库不是一个跨系统事务，不把二者假装成原子操作。

### 3.3 身份与去重规则

业务分析对象保存 workspace、shop、marketplace、child_asin、seller_sku、fulfillment 及有效期。ASIN 流量对象与 SKU 订单对象分别标识，native_grain 决定能否连接。父体映射按有效日期保存；历史报告使用当时映射，不能跟随今天的父体关系悄悄改写。

优先使用平台稳定订单行、退款交易、退货申请、评论 ID。没有稳定 ID 时，只允许契约证明唯一的复合键；相同行仅在身份可确定时去重，不能凭“内容一样、时间相近”合并真实的两笔交易。无法判断的重复候选进入待核查，不参与需要唯一订单关系的质量率计算。

file_hash 判断重复文件，business_key 判断同一业务记录，payload_hash 判断内容是否修订，三者用途分开。相同文件使用新映射重新处理属于新的处理尝试，保留旧结果，并经明确发布替换受影响版本，不重复累计。

退款撤销、退货状态更新和订单更正保存新版本；下次文件没有某一行不等于删除。只有契约明确的删除指令或经确认的数据作废操作才能使记录失效。全量快照的替换范围必须明确到对象及日期，不越界覆盖其他来源。

### 3.4 覆盖与质量状态

覆盖记录包含 source_revision、日期区间、对象范围、应有及实有分区、完整声明来源、最大业务时间、生成时间和质量原因。ready、partial、stale、missing、invalid 是按数据域及对象计算的状态，不能给整个店铺统一贴一个“数据完整”标签。

空文件、没有报错或“最新一行是昨天”均不能证明期间完整。交易型来源只有契约支持无记录代表零且覆盖已确认，才补零；否则留空。无法证明完整性的交易源不能支撑“没有退款”或成熟队列分母完整的断言。

错误页提供可下载的行级错误清单，说明修复人及操作：补列、修映射、补期间、确认来源冲突或重新上传。禁止通过直接编辑统计结果修复来源问题。

## 4 数据模型与版本边界

### 4.1 核心实体

| 实体组 | 关键字段或关系 | 不可破坏的约束 |
|---|---|---|
| 来源与导入 | SourceContract、ImportBatch、RawFile、StagedRow、CoveragePartition | 原文件及行号可查，契约与处理尝试有版本 |
| 商品与权限 | Shop、AnalysisObject、ProductMappingVersion、ScopeGrant | 店铺授权优先，映射有有效期 |
| 经营事实 | SalesTrafficDaily、OrderLine、Shipment、RefundTransaction、ReturnLifecycle | 原生粒度保存，金额采用定点数，生命周期不重复计数 |
| 辅助事实 | StockSnapshot、PriceEvent、Review、RatingSnapshot、SupportCase、OperationEvent | 采集时间与业务时间分开，评论与星级分开 |
| 修订及计算 | RecordRevision、DatasetRevision、CalculationRun、MetricSnapshot | 原记录版本不覆盖，运行固定输入清单 |
| 语义与证据 | AnnotationVersion、EvidenceFact、EvidenceMembership、MissingSignal | 标签引用原文，聚合引用完整成员或可复现成员清单 |
| 运营实体 | Incident、Detection、ReportVersion、Action、ReviewTask、Notification | 报告不可变，事件状态与动作状态独立 |
| 运行与审计 | Job、Outbox、AuditEntry、ExportArtifact | 幂等键唯一，业务变更可追溯 |

主事实表采用明确列与约束；来源扩展字段可以保存在结构化扩展列，不能把整个业务模型做成无法校验的大 JSON。所有面向业务的表带 workspace 和适用的 shop 标识；跨店铺汇总必须显式获准。金额保留原币种，不以浮点数计算，也不把不同币种直接求和。

### 4.2 一次计算读取一个稳定版本

数据版本由来源修订向量、商品映射版本、权威来源配置和规范化版本构成。运行启动时确定该清单；整个运行读取清单指向的记录版本，不在执行到一半时换成新导入的数据。记录同时保留业务发生时间和系统知道该事实的时间，支持回答“当时依据什么”和“现在修订成什么”。

CalculationRun 保存输入版本、对象范围、窗口、有效截止日、算法与规则版本、统计方法、语义标注版本、代码构建标识、运行状态及摘要哈希。大量明细使用数据库关联表或压缩成员清单，不塞进报告正文。

默认回补最近 90 天的受影响计算，但依赖追踪必须覆盖这些输入影响的成熟队列和复查任务，不能只按报告日期机械截断。更早的数据修订明确提示需人工发起历史重算。重算产生新报告，旧报告标成已被修订并链接后继，不删除旧动作或伪装成当时就已知。

## 5 数据怎么算

### 5.1 时间及窗口

所有时间戳存储为 UTC 并保留来源时区；按站点时区计算业务日期，调度按工作区时区。日期窗使用左闭右开的本地日界限再转为 UTC，跨夏令时不能把一天硬编码为 24 小时。

每项规则先取必需来源共同覆盖的最后完整日 D，再选择窗口。并非所有规则共用一个 D；缺退款数据不应阻塞销量规则，但每项结果展示自己的截止日。普通扫描排除当天未完成数据，安全反馈通过独立快速通道处理。

经营窗口为 D 前含 D 的 7 个完整日，对照紧邻之前 28 日；计数比较日均。评论当前 28 日与之前 28 日，低样本时同时扩到 56 日，仍不足则只描述样本。成熟订单窗口按 30 日观察期和来源完整性选择最近 28 个已成熟发货日及之前 28 日，窗口边界算法需用固定日期测试覆盖。

### 5.2 指标流水线

顺序固定为：授权对象 → 原生粒度校验 → 来源及覆盖 → 窗口 → 去重关联 → 分子分母 → 指标 → 统计区间 → 规则判定 → 事实生成。每一步记录排除数量及原因；不能先算比率，再补充一个笼统的数据质量提示。

| 指标 | 计算和展示 | 停止计算或降级条件 |
|---|---|---|
| 销量及流量变化 | 当前日均与基准日均比较，同时显示绝对差和原始总量 | 基准为零只显示新增量；缺日不补成零 |
| Unit Session Percentage | 同一 ASIN 及范围的 ordered units / sessions × 100 | 不向 SKU 分摊 Sessions；可大于 100%，不用二项区间 |
| 退款及退货发生量 | 按发生时间统计去重事件、有效退款金额 | 不除以同期销量冒充产品质量率 |
| 成熟订单质量率 | 窗口内符合条件的受影响订单 / 完整可观察的成熟已发货订单 | 缺订单关联或覆盖不完整时不输出权威质量率 |
| 评论主题占比 | 唯一负向或混合主题评论 / 已有效标注评论 | 低覆盖不触发趋势；检索 top K 不作分母 |
| 页面星级及可售状态 | 比较来源快照与状态变化，保留快照时间 | 无历史快照不补算；总库存不等于可售库存 |

一个订单在某 SKU 有多行或多次退款，按分析对象内订单唯一键计数一次。汇总到 ASIN 或父体时从订单明细重新去重，不能把各 SKU 的订单数相加。同一订单包含不同对象可以分别进入各对象分母，但跨对象总计必须重新去重。

队列归属使用该订单中该分析对象的首次发货时间。分批发货仍按已冻结的“订单口径”观察，不将未发货部分伪装成已发货数量。补发或换货订单只有可靠原订单关系才排除重复原始销售；关系缺失保留不确定性。

退款在首次发货后的 30 日半开区间内发生，并截至计算快照按原退款链扣除撤销后净额大于零，才计入对应有效退款订单。观察窗外的新退款单独展示；对窗内退款的后续撤销会修订历史有效性。部分金额退款计一笔受影响订单，不能推断全部件数有质量问题。退货申请与收到退货按来源定义固定择一，不把两种状态各算一次。

订单无法关联的售后记录单独显示发生量和缺口；不丢弃这些记录后声称总体质量率正常。只能在明确可证明完整的子范围计算，并显式标为该范围结果；默认全对象成熟率规则暂停。

### 5.3 统计方法及结构变化

规则阈值直接引用 V2 第 9 节，保存 rule_config_version；不在技术文档另建一套相近阈值。比率区间使用 Wilson 95%，两组独立二项比例差使用 Newcombe，主题多重检验采用 Fisher 双侧加 BH，检验族固定为同对象同轮扫描预定义的全部合格主题。不能只对显著主题再校正，也不能把重复扫描视为新增独立样本。

同一买家、重复交易或重叠观察可能削弱独立假设，报告保留统计限制；显著差异只支持观察到变化，不支持原因已被证实。统计库方法与参数显式指定并用已知答案验算，不依赖随版本改变的默认值。

父子体分析同时展示整体、子体和构成比例。若做结构分解，使用相同指标分母对应的权重：订单质量率用订单分母，销量份额不能代替订单权重。共同子体上的变化可分成权重变化和子体率变化，新进入、退出或缺数据的子体列为残余项；条件不满足时只并列展示，不能给出伪精确归因百分比。

### 5.4 语义与安全计算

离线标注按文本版本、标签体系、模型版本及提示版本唯一缓存。先识别语言，再输出受限标签、极性、原文片段及字符位置；片段必须能在原文中精确找到。无效输出进入重试或待核查，不把失败条目归为中性。趋势分母和标注覆盖率在同一文本版本集合上计算。

检索支持对象、期间、主题、极性、语言和关键词组合。中英文分词、产品别名与明确短语匹配构成默认方案；短中文词不能只依赖英文全文索引。原文及证据位置保持不变，检索索引可重建。是否增加向量检索由冻结测试集的 Recall@10 决定，不把向量数据库设为产品前提。

安全通道在导入可用文本后立即运行高召回词组、否定语境规则及语义核查，不等待全量扫描或评论覆盖达标。模型不可用时把疑似线索交人工，注明“尚未确认”，不能把规则匹配直接断言为真实事故。安全线索可先进入待核查事件，再关联完整报告；不自动下架、发信或发起平台操作。

## 6 怎么追溯及如何约束报告

### 6.1 引用链

每条报告结论指向 EvidenceFact；事实指向 MetricSnapshot 或原文片段；指标指向 CalculationRun 和参与记录版本；记录版本指向来源契约、原文件及原始行号。用户从页面数字能逐层查看计算式、分子分母、排除记录及来源，不必阅读程序日志。

例如“退款率为 6%”必须能展开为“12 / 200 个成熟订单”，列出这 12 个受影响订单、200 个分母订单、首次发货及退款时间、退款撤销处理方式、数据截止日和覆盖状态。若来源只给 6%，则显示“来源报表值”，不得伪造这两份订单清单。

事实有统计、状态、文本、人工核查四类。人工核查保留提交者、时间、附件和判断范围；不是自动成为训练真值，也不能改写计算结果。缺失数据保存为 MissingSignal，包含阻塞的判断、所需来源、负责人和补齐后的重算入口。

### 6.2 候选与确定性排序

标准候选由场景规则枚举，分别记录支持、矛盾、缺口和待核查动作；LLM 不新增标准候选原因类型或更改次序；自主调查的新假设另存为探索线索。候选排序采用版本化的明确比较序列：人工已核实状态、对象及时间适配程度、所需来源完整程度、独立支持事实数量、未解决矛盾数量、稳定候选 ID。

独立支持事实按来源经历或事实族去重，同一退款在报表、工单和评论里出现不能自动当成三条独立支持。人工核实仅在其核查范围内有效。排序高不代表概率高；没有校准依据不输出原因概率或确定的损失估算。

### 6.3 生成与校验

报告主体由确定性模板填入事实、候选、缺口及动作槽位。报告解释节点只解释已有材料；自主决策节点另遵循第 11.12 节，返回结构化 claim，每条绑定允许的事实 ID，不接受任意 SQL、任意工具调用或评论中的指令。数字、对象、期间、单位、引用存在性和因果措辞分别校验。

无法仅靠字符串校验保证所有自由文本正确，因此关键指标、确定性结论和原因状态由服务端生成。模型自由解释不得新增无引用事实；校验失败直接使用规则报告，不先展示未校验内容。记录失败原因、模型及提示版本、耗时和用量；敏感原文不进入通用日志。

新报告与旧报告的差异分为数据修订、规则变化、语义版本变化及人工补证，明确哪些结论改变。历史报告不因升级模型而自动重写；主动重标注产生新计算和报告版本。

## 7 怎么处理及何时关闭

### 7.1 事件聚合与并发

事件业务键为工作区、授权分析范围、问题族。销售转化、售后体验、可售库存、安全保持独立问题族，可相互链接。数据库约束保证同键最多一个开放事件，检测更新在事务中执行，不能靠先查后插避免重复。

连续扫描附加检测和报告版本。只有出现新完整业务日才增加持续天数；同一天重复导入或人工重跑不延长持续时间。关闭后 30 日内同问题复发重新打开并保留历史，超过 30 日建立新事件并链接旧事件。单纯历史数据纠错标为结论修订，不能当成新的现实复发。

人工合并、拆分要指定涉及的检测、报告和动作归属，并记录重定向和理由；不允许借合并把未授权店铺数据带入事件。页面提交带实体版本，版本过期返回冲突和最新状态，防止两名运营互相覆盖处理记录。

### 7.2 状态与动作

| 对象 | 状态流转 | 条件与处理 |
|---|---|---|
| 事件 | 待处理 → 处理中 → 观察中 → 已关闭 | 关闭必须有原因及核查记录；指标恢复不是唯一关闭原因 |
| 数据阻塞 | 正常 ↔ 待补数据 | 作为独立阻塞标记，保留事件主状态及缺口负责人 |
| 暂缓提醒 | 未暂缓 ↔ 暂缓至指定日期 | 不停止扫描，严重安全线索仍提醒 |
| 动作 | 待执行 → 执行中 → 已完成，或已取消 | 完成需结果及实际完成时间；取消需理由 |
| 复查 | 未到期 → 待复查 → 已复查，或等待数据 | 观察期和来源未满足时不能写“效果已验证” |

确认一个候选原因不等于关闭事件，分派负责人不等于开始生效。动作记录目标对象、问题、证据、执行人、完成标准、截止时间、实际生效日、结果、观察指标及复查日。调查产物、草案和待核查任务可自动保存；正式动作或指派仅在匹配预授权规则或用户确认后执行，按命令幂等键避免报告重算或图恢复时重复创建。

销量类动作按实际生效后的 7 个完整日复查；退款类等待相应发货队列成熟且来源完整。复查同时展示动作前后数据与期间其他经营事件，只能写“指标改善、未改善、尚不可判断”，没有额外证据不能写“该动作导致改善”。

已恢复、误报、数据错误、重复事件、业务接受风险等关闭理由分别记录。接受风险不能伪装成问题解决；再次达到复发规则仍可重新打开。已完成动作需要修正时增加更正记录，不抹掉原执行历史。

### 7.3 提醒和导出

站内提醒只针对新事件、恶化、重新打开、分派及复查逾期。恶化沿用 V2：紧急级别升高，或相对上次提醒的异常幅度增加至少 25% 且仍满足触发条件。通知幂等键基于事件、提醒类型及业务变化，不仅依赖任务 ID。

报告导出固定到 report_version；事件 CSV 固定查询及数据版本。生成时和下载时均重新校验用户权限，采用有期限的下载链接；跨店铺结果不能共享到无权限用户。CSV 防公式注入，HTML 中原文转义，不运行评论或模型输出中的脚本。

## 8 接口与页面契约

接口统一使用版本前缀、稳定 ID、分页和结构化错误。金额以十进制字符串与币种返回，日期带业务时区，统计值带单位、分母、覆盖和截止日。空值保留 null 并提供原因，不返回 0 混淆未知。

| 接口组 | 典型操作 | 返回或约束 |
|---|---|---|
| 导入 | POST /v1/imports；GET /v1/imports/{id}/preview；POST /v1/imports/{id}/publish | 创建及发布支持幂等键；异步返回 202 和 job_id |
| 扫描 | POST /v1/scans；GET /v1/jobs/{id} | 同输入返回既有任务，进度区分排队、运行、失败、完成 |
| 事件报告 | GET /v1/incidents；GET /v1/incidents/{id}；GET /v1/reports/{id} | 当前状态与不可变报告版本分开 |
| 证据 | GET /v1/evidence/{id}；GET /v1/evidence/{id}/records | 分页明细，按源对象权限过滤，保留原行号 |
| 处理 | POST /v1/incidents/{id}/commands；POST /v1/actions；POST /v1/reviews/{id}/complete | 明确命令，校验实体版本、权限和状态转换 |
| 查询导出 | POST /v1/query/interpret；POST /v1/exports | 返回 query 或 investigate 类型及定位依据；未解歧义须选择 |
| 自主调查 | POST /v1/investigations；GET /v1/investigations/{id}；POST /v1/investigations/{id}/commands | 返回 202 和运行 ID；支持 clarify、continue、cancel 命令及实体版本 |
| 变更提案 | GET /v1/change-proposals/{id}；POST /v1/change-proposals/{id}/commands | approve/reject 针对精确 payload_hash 和版本；确认与执行分别留状态 |

幂等键按用户、操作及授权范围绑定请求摘要；相同键不同请求返回冲突。错误至少包含 code、message、field_errors、retryable、request_id。需要补数据是业务状态，不一律返回服务器错误；无权限、状态冲突、来源无效、临时不可用分别处理。

自然语言解析对象、期间、指标、主题和查询/调查意图，服务端复核授权及枚举。模糊指令先按第 11.12 节定位，不能跳过可查映射直接让人补齐。模型不可用时普通查询及 L1 报告继续可用，L2 明确显示暂停或部分完成，不宣称已完成自主调查。

五类页面分别为事件队列、报告、动作复查、商品映射、数据源。事件列表显式显示截止日、数据状态、负责人和复查日；报告并列展示事实、候选、反证和缺口。任务状态采用轮询即可，先不增加实时通信基础设施。所有页面覆盖加载、空数据、部分数据、无权限、失败重试和旧报告已修订状态。

## 9 后台任务与故障恢复

### 9.1 任务投递与执行

业务事务同时写 Job 和 Outbox。投递器把 Outbox 转成消息，成功后标记；崩溃可导致重复投递，因此工作进程必须幂等。不得宣称消息组件能提供业务上的“恰好执行一次”。

任务幂等键由任务类型、工作区、对象范围、输入版本和算法版本构成。工作进程领取有期限租约，更新心跳；重领产生新的 fencing token，旧进程完成时不得覆盖新持有者结果。长任务按分区记录检查点，中断恢复不从头重复提交已完成业务变更。

每工作区普通扫描互斥，新导入只把受影响范围并入下一轮；安全任务使用独立队列和有限保留并发，不被普通扫描长时间阻塞。避免长数据库事务覆盖整个扫描，结果先写暂存，完成后原子发布。

### 9.2 重试及补跑

网络超时、限流和临时数据库错误按第 11.4 节由唯一责任层退避重试；字段错误、权限错误、无效模型输出超过上限转人工处理，不无限重试。模型沿用需求的单次 30 秒超时加一次重试，之后使用规则报告。不同类型任务可独立限流，设置工作区用量与并发预算，避免批量回补挤占日常扫描。

每天按工作区时区 08:00 调度，同一计划时间唯一。调度器只运行一个有效实例，数据库唯一键仍作为最后保障。服务离线后对遗漏范围合并补跑并显示延迟，不逐个历史计划重复提醒。任务取消是协作式的，已发布结果保留，未发布结果不激活。

后台页面显示最后成功导入、完整业务日、任务积压、失败原因、标注覆盖、模型耗时用量及备份状态。任务重跑保留尝试记录；日志用 request_id、job_id、run_id、report_id 贯通，不能把订单个人信息打印出来。

## 10 权限存储与部署

权限采用角色能力与店铺商品范围的交集。管理员可管理来源及授权，运营处理其范围内事件，质检与售后处理被授权对象和动作。负责人映射不等于自动获得数据权限；权限校验覆盖列表、聚合、搜索、证据、后台任务及导出。

建议浏览器与 API 同源部署，使用服务端会话、安全 Cookie、CSRF 防护、TLS 和登录限流。框架自带的用户权限不等于店铺对象权限，需要应用层统一实现并测试。数据库运行账号与迁移账号分离；本次使用应用层统一对象授权，不另启用行级安全；所有读写路径都必须通过隔离测试。

仅保存诊断需要的数据，来源含姓名、地址、电话等信息时在规范化阶段去除或遮蔽；原文件也受更严格访问控制。订单 ID 可作内部关联键，展示时按角色遮蔽。模型只接收必要脱敏片段，模型供应商、部署区域和允许传输的数据类型确认前，不调用真实客户数据。

原文件和审计记录默认按需求保留 180 天，可按来源授权缩短。删除需覆盖原文、派生标签、索引、缓存及导出；不能为了可复现无限保留已到期个人信息。历史报告保留允许保留的聚合和删除标记，明确哪些原始证据已不可回查。备份按期限轮换，恢复后先应用删除台账再开放查询，避免恢复已删除数据。

按已确认的单台云服务器部署，建议容器编排管理入口、API、工作进程、调度、数据库与消息组件；文件使用持久卷，备份保存到独立故障域。单机属于可恢复部署，不是高可用承诺。建议恢复目标 RPO 不超过 24 小时、RTO 不超过 4 小时，作为待确认运行目标，必须通过恢复演练证明。

每日备份数据库、原始文件及其校验清单、配置与版本信息；备份完成不等于恢复可用。发布前从备份恢复到隔离环境，核验报告到原行引用、权限和任务去重；禁止在恢复演练中向生产发通知或调用外部模型。磁盘接近上限时停止新导入并提示，避免继续写入造成数据损坏。

## 11 完整技术方案与选型决策

### 11.1 推荐组合及决策依据

推荐采用 Python、Django、Django REST Framework、PostgreSQL、Celery、Redis、React、TypeScript、Ant Design 和 Docker Compose。标准诊断采用 Python 固定流程，自主调查采用 LangGraph StateGraph 与 PostgreSQL checkpointer，模型接入采用 HTTPX 与 Pydantic；不增加 LangChain create_agent、独立向量数据库或微服务。以下主体组件组合已由用户确认，兼容性和业务能力仍须逐项验证；“已查阅官方文档”不等于已经完成组件兼容、业务评测或容量验证。

选型依据是小团队、单服务器、文件接入、固定规则、可追溯结果和持续多天的人工处理。业务复杂性集中在数据质量与状态一致性；本次已确认开放式自主调查及受控内部写入；第 11.3 节区分单次调用、固定流程与 Agent，第 11.12 节定义新增调查的执行契约。没有把任何本次范围内功能推迟到后续产品版本。

| 层次 | 推荐组件及用途 | 备选与取舍 |
|---|---|---|
| 语言与依赖 | Python 3.13、uv；TypeScript、Node.js 24 LTS、pnpm | 两种语言分别服务计算与浏览器界面；不增加 Java 或 Go 服务 |
| Web 后端 | Django 5.2 LTS、DRF、Gunicorn WSGI | FastAPI 可行，但本系统更需要事务、权限与管理能力；不另搭第二套 ORM 与迁移 |
| 数据访问 | Django ORM、Django migrations、psycopg 3 | 批量导入使用参数化 COPY 到暂存表，复杂统计使用审查过的参数化 SQL；不引入 SQLAlchemy |
| 主存储 | PostgreSQL 18、JSONB 扩展字段、B-tree 和 GIN 索引 | SQLite 不作为多人服务主库；当前规模不增加 ClickHouse、数仓或读写分离 |
| 任务执行 | Celery 5.6、Redis、单实例 Celery Beat | Celery 执行单个任务；不用 Canvas 再保存一套诊断步骤依赖，也不同时引入 APScheduler |
| 诊断流程 | Python 固定检查；LangGraph StateGraph 自主调查；langgraph-checkpoint-postgres | 固定检查保存 StepResult；自主调查由图 checkpoint 恢复，两者不重复驱动同一阶段 |
| 模型接入 | HTTPX、Pydantic 2、版本化提示及模型配置 | 不引入 LangChain Agent；标准三个业务接口加 decide_investigation 调查决策接口，供应商协议由适配器处理 |
| 指标统计 | PostgreSQL 聚合、Decimal、SciPy、statsmodels | 不使用 LLM 算数；不引入 Spark；Pandas 不作必须依赖或整库内存计算主路径 |
| 证据检索 | PostgreSQL 全文检索、应用层中英文分词、别名词典 | 默认无向量服务；检索验收未达标时在冻结前调整方案，不以“以后优化”通过验收 |
| 前端 | React 19、TypeScript、Vite、Ant Design 6、React Router | 内部工作台无需 SSR，故不引入 Next.js；Vue 可替代，但推荐方案只保留 React 一条主线 |
| 请求与图表 | TanStack Query、生成的 API 类型、ECharts | 服务端数据统一缓存与失效；少量页面状态用 React，不另引入 Redux |
| 文件及导出 | 持久卷、SHA-256、Python CSV、Django 模板、JSON | CSV 与 HTML/JSON 满足需求；不增加在线 Word/PDF 渲染服务或 MinIO 集群 |
| 服务入口 | Caddy 2、TLS、同源静态站点与 API | Caddy 统一入口；不同时叠加 Nginx，浏览器无需跨域令牌方案 |
| 部署恢复 | Linux、Docker Engine、Compose、pg_dump、restic | 单机足够当前目标；不使用 Kubernetes，备份必须离开该服务器 |
| 测试质量 | pytest、pytest-django、Hypothesis、Vitest、Testing Library、Playwright、Locust | 分别覆盖业务、边界、组件、流程和负载；不以页面截图代替计算验证 |
| 工程检查 | Ruff、mypy、ESLint、TypeScript 检查、pip-audit 与 pnpm audit | CI 运行同一检查脚本；依赖与镜像锁定，不在生产启动时安装浮动版本 |

表中明确的版本系列为拟定兼容基线，不是已锁定补丁清单。DRF、Vite、Redis 及其他库在第 11.10 节的依赖解析中确定受支持且兼容的版本；不得因本表没有补丁号而使用 latest 镜像或无锁安装。Python 3.13 与 Django 5.2 的支持关系可由官方说明核对，其余组合仍需实际安装及冒烟验证。

### 11.2 后端结构与业务边界

采用模块化单体，模块按 identity、catalog、ingestion、metrics、semantics、diagnostics、operations、jobs、audit 划分。名称表示拟建领域边界，不对应或沿用历史工程目录。HTTP 层处理协议、序列化和授权，服务层处理业务命令与事务，查询层处理授权后的列表及聚合，纯计算函数不依赖请求对象。

业务主写路径必须经过服务层。Django Admin 仅供授权管理员维护来源、映射和配置；报告、指标快照、事件历史和已完成动作以只读方式展示，不允许绕过业务命令直接改表。复杂统计可用 SQL，但禁止模型生成后直接执行 SQL。

DRF serializer 定义公共 API 字段；Pydantic 定义模型输出和内部计算结果。二者不各自重新定义金额、时区和枚举的业务规则：共用领域类型和验证函数，分别做协议映射。drf-spectacular 生成 OpenAPI，openapi-typescript 生成前端类型；在 CI 检查契约与客户端类型同步。

用户权限采用 Django 账号与服务端会话。所有店铺数据查询通过统一 scope 入口，角色能力与对象范围同时校验；后台任务保存发起身份，系统定时任务用限定工作区的服务身份。执行前及结果下载前检查当前授权。数据库迁移账号和运行账号分离；本次采用应用层对象授权，不启用第二套 PostgreSQL RLS 规则，必须通过跨店铺列表、聚合、证据和导出泄漏测试。

### 11.3 业务任务分解与执行策略

先按业务中的最小决策单元分工，再选运行框架。同一项业务可以由代码、一次模型调用和人工确认共同完成；不能把“评论分析”“诊断”整个模块笼统标成 Agent。以下 B01 至 B40 覆盖原 FR-01 至 FR-12，B41 至 B46 补齐本次确认的自主调查与受控写入，覆盖新增 FR-13。覆盖当前需求不等于穷尽亚马逊运营的所有业务，广告投放、利润核算等排除项不因本节而自动纳入。

**五种执行方式及人工责任**

| 类型 | 控制权与适用条件 | 结束和失败处理 |
|---|---|---|
| D 确定性处理 | SQL、规则或普通代码已有明确答案；输入决定结果 | 校验通过提交；输入不成立则给出具体缺口，不交模型猜 |
| S 单次语义调用 | 所需上下文已齐；一次结构化输出能完成明确语义任务 | 校验 schema、引用及业务约束；失败标记未完成或模板降级 |
| F 固定工作流 | 步骤及允许分支事先已知；可串行、并行、按数据数量展开 | 每个必查项记录结果或不可检查原因；到达终态结束 |
| P 受限动态计划 | 用户组合了现有能力，执行前需要生成一次有限计划；执行中不自主改计划 | 先校验完整计划再执行；失败返回缺口，不边执行边自由扩展 |
| A 受控 Agent | 下一步确实依赖刚取得的新证据，由模型选择工具、参数和是否继续 | 明确工具、权限、成本及步数上限；无新证据、超限或需人工即停止 |

H 表示人工确认或业务决策，可以叠加在以上任一类型上，不能因为有审批就称为 Agent。定时排程由 Beat/Job 处理，F 表示业务步骤的固定编排，两者不同。这里的动态计划指执行计划生成，不是算法中的动态规划。按子 ASIN 数量展开并行查询、按缺失数据走预设分支，仍属 F，不属 P 或 A。

模型调用次数按一个业务单元的逻辑调用计算，网络重试另外受第 11.4 节预算约束；批量处理一千条评论会产生多个 S 单元，但不会因此成为 Agent。单次调用不是硬性追求：输入过长、不同权限或输出无法稳定校验时，应拆分成固定工作流。

**五条调查路径的依赖与停止条件**

销量路径先确定窗口、覆盖和对象，随后可并行查可售/库存/购物车、流量、转化、价格促销、运营变更和反馈。转化需有效分母；无流量数据时记录不可检查，不从差评推出销量原因。检查的展示顺序表达排查优先级，不表示前项通过才能检查后项。

转化路径先验证会话与订单件数粒度，再检查子体占比变化；按同一对象及窗口比较可售、购物车、价格促销、Listing 变更与反馈。不能把 SKU 层销量复制成多份 ASIN 会话。结构变化与子体真实变化分列。

退款退货路径先分发生期异常和成熟订单队列，再按原因、子体及履约分层；仅有可靠关联时查处置、工单、批次和运营变更。成熟不足、关联不足分别返回缺口，不能筛掉未关联项后宣称质量恢复。

评分评论路径先核实页面快照时间、采集覆盖及变体映射，再计算主题与极性趋势，并交叉检查退款和工单。不存在对应来源时注明未检查；页面下降、采集均分下降和投诉主题增长是不同事实。

安全路径直接保存原文、定位对象、检查否定与假设语境并交人工核查；规则发现可疑线索即可进入，不能让模型判“无风险”自动关闭。以上路径在必查项均为完成、不可检查或不适用时停止；模板或单次说明后发布，不因根因尚不明确而不断调用工具。

简单组合问句仍按 B32 的固定模板执行；无需反馈循环的组合可在白名单内用一次结构化任务分解，再由固定代码执行。范围内的“分析原因”转 B41 至 B44，不以旧版受限查询范围拒绝。暂不另建任意图 DSL 或通用动态计划平台。

模糊指令的定位遵循需求第 5.3 节：先使用可见上下文，再查询授权工作区内的映射与异常摘要；多个合理站点不能只选最大异常者。明确跨站点调查逐站点计算并列报告，保留独立时区、币种和数据截止日。固定检查与自主探索共同构成一次完整调查，用户不需要了解 L1/L2 或选择 LangGraph。

**框架选择及责任边界**

| 执行范围 | 推荐实现及原因 | 不选其他方案的具体理由 |
|---|---|---|
| 当前 D、S、F、H | Python 显式服务函数、HTTPX/Pydantic、Celery；业务进度持久化到 Run/StepResult | 固定依赖和分支可直接测试；单次语义调用没有自主工具循环，不需要 Agent harness |
| 无反馈循环的组合查询 | Pydantic 计划 schema、有限白名单执行器，仍可用 Python | 不为最多几层的已校验计划构建通用工作流语言；若开始出现反复重规划，重新归类为 A |
| 已确认 B43/B44 自主调查 | LangGraph StateGraph 管理调查状态、工具节点、条件边与 checkpoint | 自主决策循环和可恢复执行有明确需求；框架收益对应 A 的实际复杂性 |
| LangChain 是否同时需要 | 不采用 LangChain create_agent 上层循环；LangGraph 节点调用统一模型适配器 | LangChain 可用于模型/工具适配或标准 create_agent 循环；只有所需能力确能减少维护时才引入相应包 |
| 其他框架或自研 Agent | 当前不用多 Agent 框架、独立持久化工作流平台或自研开放循环 | 单机小团队没有已证明的协作或跨系统事务需求；自主调查使用成熟图运行时，不自研 checkpoint |

LangGraph 同样支持固定流程，不能用“是固定流程”证明它不适用；这里选择 Python 是因为有限路径不需要通用图运行时，且结果审计本来就在业务数据库。引入 LangGraph 也不必天然产生双重状态：应让它负责调查执行 checkpoint，业务表负责指标、证据、事件和动作。Celery 只分发调查运行，图负责内部恢复；不得再由 StepResult 驱动同一调查的另一套恢复。正式结果发布仍经过带幂等键的领域服务，图 checkpoint 不能代替业务审计或外部副作用去重。

当前固定诊断骨架为 ValidateInputs → LoadMetrics → CollectEvidence → BuildCandidates → Explain → Guard → Publish；五条路径在 CollectEvidence 内选择预定义检查。workflow_version 标识代码及分支契约，不引入图 DSL。缺数据发布有限报告；补数创建新输入版本。人工处理与复查通过 operations 的业务状态持续保存，旧运行恢复必须使用兼容流程版本，不能拼接语义不同的步骤结果。

本次确认的组合是“确定性主系统 + LangGraph 有界自主调查 + 受控业务写入”。标准 D/S/F 使用 Python；B43/B44 使用 LangGraph；所有修改都由业务命令服务执行。LangChain create_agent 不参与控制同一循环；若 LangGraph 的传递依赖包含 langchain-core，不等于另外采用了 LangChain Agent 框架。模型服务及全部依赖补丁尚未冻结。

### 11.4 调度执行状态与重试责任

| 组件或实体 | 唯一职责 | 不负责的内容 |
|---|---|---|
| Celery Beat | 周期唤醒调度检查、Outbox 投递和恢复检查 | 不保存业务截止日或判断事件是否解决 |
| Job 与 Outbox | 保存待执行工作、投递状态、租约、尝试次数及下次运行时间 | 不复制事件处理状态 |
| Celery 与 Redis | 传递 job_id，把任务交给可用工作进程 | 不作为唯一进度库，不保存权威业务结果 |
| CalculationRun 与 StepResult | L1 固定输入快照、步骤输出引用、完成进度及校验摘要 | 不驱动 L2 图恢复 |
| InvestigationRun 与图 checkpoint | L2 调查范围、执行状态和图内恢复位置 | Job 只负责运行级调度；预算和命令回执以数据库账本为准 |
| Incident 与 Action | 保存事件、负责人、动作及复查的业务事实 | 不以 Celery SUCCESS 代替完成或解决 |

Beat 每分钟检查工作区计划与到期复查，按计划时间唯一键写 Job；Outbox 投递任务同样由 Beat 唤醒。长周期计划保存在业务数据库，不使用 Redis 的长时间 ETA 消息。所有任务仅传 ID，工作进程领取租约后从数据库加载输入和授权。

普通任务基础配置建议 acks_late=true、worker_prefetch_multiplier=1、task_ignore_result=true，序列化仅允许 JSON，不使用 Celery result backend 作为业务进度。Redis visibility timeout 建议 1 小时，普通任务分片目标小于 5 分钟、硬超时初始值 10 分钟；整轮扫描可由多个分片组成。上述为运行配置初值，需故障测试调整，visibility timeout 不是执行锁。

采用 DB 任务恢复器统一决定是否重跑：默认不启用业务任务的 Celery autoretry，也不在 HTTP 客户端外再叠加通用重试装饰器。临时执行失败记录 retry_wait、next_run_at 和错误码，恢复器到期重新写 Outbox；普通任务初始最多 3 次执行尝试，超过后进入 failed，人工重跑创建有链接的新尝试记录。

模型调用是唯一单独预算：每个 request_key 最多两次网络尝试，即需求中的 30 秒超时加一次重试。尝试次数、输入摘要和有效返回都持久化，外层任务重启不能重置预算。发送前崩溃可能消耗一次预算；请求已发送但未保存返回时，供应商若不支持幂等请求，无法保证不重复计费，超出剩余预算则降级，不能无限补发。标准报告的模型业务失败降级为模板；L2 失败记录 partial/failed 及已有证据，不把 L1 降级报告冒称自主调查完成，均不抛给外层无限重算。

每次领取 Job 增加租约代数；写 StepResult、发布报告及修改事件时，在短事务中核验租约代数和有效期。已失效旧进程不得发布任何副作用。StepResult 的唯一键为 run_id、step_name、input_hash，完成结果可复用；外部模型结果不假设可重复生成。发布报告、关联事件、写审计和提醒 Outbox 在同一事务中提交，唯一 publication_key 防止重复发布。

Redis 消息丢失后，恢复器扫描超时未开始或租约过期的 Job 补投；重复消息遇到有效租约或已完成结果直接退出。恢复器也使用数据库锁和唯一键，不能由多个检查任务同时增加重试次数。普通扫描、语义任务和安全任务分队列；安全保留独立工作进程。

### 11.5 数据库文件与计算落地

PostgreSQL 是唯一业务事实库。主键采用稳定 UUID，导入及事实业务键按来源、店铺、对象、粒度建立唯一约束；允许为空的 SKU 和履约字段需规范化或采用明确的空值唯一策略，避免 SQL 默认空值行为绕过去重。映射有效期不得重叠，开放事件约束按状态建立部分唯一索引。

常用查询索引从授权范围开始，追加对象、业务日期或状态；任务索引覆盖 status 与 next_run_at；原行引用覆盖 import_id 与 row_number；版本查询覆盖 business_key 与 revision。初始不分区、不分库，先用 EXPLAIN ANALYZE 和压测确认慢点，再决定必要索引，禁止按每个字段盲目建索引。

CSV 使用流式解析和分块暂存，建议每块 5,000 行作为测试起点，不把整份报表及历史事实载入 Python 内存。文件先放在非公开路径，哈希完成后写内容寻址的不可变文件；同一物理文件复用不改变按来源及店铺独立授权。大聚合在 SQL 完成，统计函数只读取必要的分子分母或受控样本。计算结果使用版本键缓存到 MetricSnapshot，缓存命中仍须检查权限。

原文件、附件和导出通过 FileStore 接口访问，默认实现为服务器持久卷。备份使用 restic 加密复制到独立对象存储，数据库用一致性 pg_dump；通过 PostgreSQL 导出快照并让 pg_dump 与文件清单查询使用同一快照，确定必须备份的不可变文件；快照会话在导出结束前保持有效。备份期间暂停清理任务，核验清单中的每个哈希都存在。备份清单和数据库快照对应，不用随意复制运行中的数据库目录替代一致性备份。

### 11.6 模型检索与成本控制

模型适配器提供 classify_feedback、interpret_query、explain_evidence、decide_investigation 四个接口，输入输出均为受限 schema。HTTPX 统一管理连接池、连接及读写超时和响应大小，调用外层另设 30 秒总截止时间，不能把读超时当作整次请求时限；Pydantic strict 校验类型、枚举及禁止额外字段，业务校验再检查原文位置、证据 ID、对象范围和允许措辞。结构正确不代表事实正确，两层不能合并。

建议使用托管云端文本模型，当前 8 核 16 GB 主机承担应用和数据库，不同时部署大模型推理。模型供应商、部署区域及真实数据传输权限仍需用户明确；这一未决项不能由框架选型代替。适配层不得假设所有服务的 OpenAI 兼容接口都支持同样的 schema、限流和用量字段，选定服务后用契约测试逐项核对。

模型配置保存 provider、endpoint、model_id、可用模型修订标识、prompt_version、schema_version、参数和计价配置。只用模型别名且供应商会更换底层模型时，应标记版本不可完全固定；运行结果仍保存，不承诺相同提示重跑一定相同。默认不自动切换另一供应商，避免数据区域和标签口径未经确认就改变。

单条反馈按原文有效长度分块，保持片段回到原文的位置映射；模型失败的片段使该条标注不完整，不计入有效趋势分母。分块大小随选定模型的上下文预算配置，长文本既不静默截断也不把多块当多条评论。解释只发送经过授权的事实摘要和有限证据片段，不传全店报表。

成本按任务、模型、输入输出 token 和已知单价记录；用量缺失单列，不能当作零费用。首次标注成本估计为待处理文本数乘以抽样平均 token，再按真实报价计算；保存失败及重试成本。工作区设置日预算和最大并发，达到预算后暂停普通语义增强并提示，规则诊断继续，安全线索仍走规则及人工核查路径。

检索先按授权对象、期间和标签过滤，再进行 PostgreSQL 全文检索。中文使用 jieba 及版本化产品词典，英文使用全文索引词干处理；中文 token 写入 simple 配置的检索字段，原文片段独立保存。精确 ASIN、SKU 和短语查询优先，短中文词用受范围限制的字面匹配补充。排序使用明确权重和稳定 ID，不将 PostgreSQL 默认排名冒称 BM25。

通过固定中英文及同义表达测试验证 Recall@10。若分词和别名仍不达标，在冻结前提交 pgvector 混合检索的替代决策及模型成本评测；该分支要解决后才能冻结检索实现。当前不预装向量服务，也不把未来添加向量作为本次功能验收的免责条件。

### 11.7 前端与接口协作

React 实现五类业务页面，Ant Design 负责表格、表单、分页和状态交互，ECharts 展示时间窗及指标对比。React Router 管理页面路由；TanStack Query 管理服务端数据和任务轮询。筛选条件进入 URL，便于运营复现同一查询；店铺切换及退出登录清空对应缓存，不能短暂展示上个账号数据。

权限由服务端最终决定，按钮隐藏仅用于交互提示。前端不重新计算退款率、显著性、原因排序或关闭条件；展示后端的版本化结果。动作提交带实体版本，遇到 409 展示最新记录及冲突内容，让用户重新确认，不能自动覆盖或默默重发。

Django session 使用 HttpOnly Cookie，前端提交 CSRF token；同源部署不开宽泛 CORS，不把长期 JWT 放在 localStorage。初始请求采用分页，证据明细按需加载；任务轮询建议前台 5 秒、后台降频，完成或失败后停止。前后端共享 OpenAPI 契约及固定 mock，允许契约冻结后并行开发。

### 11.8 单机部署与运行责任

Docker Compose 管理 Caddy、API、普通 worker、语义 worker、安全 worker、Beat、PostgreSQL 和 Redis。Node 仅在构建阶段生成静态文件，生产不运行前端开发服务器。仅 Caddy 暴露 80/443，数据库和 Redis 只在内部网络可见；TLS 所需域名与证书配置由部署清单明确。

建议初始资源预算为 PostgreSQL 4 GB、普通 worker 3 GB、语义及安全 worker 合计 2 GB、API 1.5 GB、Redis 0.5 GB，至少给系统、文件缓存及入口保留 3 GB，其余作余量。普通 worker 并发起点为 2，语义为 2，安全为 1，API 为 2 个进程；这些是负载验证起点，不是实测容量承诺。Redis 采用持久化及 noeviction，不与可随意淘汰的业务缓存共用策略。

健康检查分存活与就绪：API 可查询数据库才就绪；Redis 故障显示任务延迟，普通只读报告仍可用；数据库不可用不接收业务写入。Beat 心跳超过 3 分钟、任务积压、磁盘占用超过 80%、备份超过 26 小时未成功生成运维异常记录；磁盘超过 90% 暂停新导入。这些运行阈值版本化，首次压测后确定正式值。

JSON 结构日志输出到标准输出，Docker 配置日志轮转；应用页面显示任务及数据源异常，运行手册提供日志查询与服务恢复命令。无需先部署 Elasticsearch、完整监控集群或外部追踪平台。单机完全宕机时站内通知不可达，值守通过云平台已有主机告警和人工巡检处理；不把站内提示宣称成外部宕机通知。

密钥通过只读 secret 文件注入并限制系统权限，不进入镜像、仓库和数据库明文配置。每次发布保存镜像 digest、迁移版本、规则及提示版本和依赖锁摘要。涉及字段删除或类型变化时先做兼容迁移；不可逆迁移的回退需要恢复窗口，不宣称回滚镜像就能回滚数据。

### 11.9 测试工具与证据要求

后端使用 pytest-django 连接真实 PostgreSQL，覆盖唯一约束、事务、权限及并发；不以 SQLite 替代验收数据库。Hypothesis 验证金额合计、重复导入幂等、计数界限和时间窗等不变量，已知答案案例验证 Wilson、Newcombe、Fisher 及 BH。数据库与 Redis 故障恢复测试必须运行真实 Celery worker，不能只用 eager 模式。

前端用 Vitest 与 Testing Library 验证错误、空态及冲突交互，Playwright 验证导入到关闭的完整链路和跨账号访问。Locust 在目标机器验证 10 人并发、导入期间读取、已有标签的全量扫描及百万记录压力档位；报告 CPU、内存、磁盘、数据库连接和队列等待，不能只报告平均响应。

模型评测用受版本控制的独立脚本和金标数据，记录原始输出、schema 失败、语义分数、严重安全漏检及成本。数据库事实引用和证据约束独立验收，不让模型自评是否正确。采用 pytest 与数据文件即可，不强制 LangSmith 或其他云评测服务。

CI 至少执行锁文件安装、后端静态检查及测试、OpenAPI 差异、前端类型与组件测试、容器构建和关键 E2E。代码托管平台未指定时，用仓库内同一命令脚本承载检查，不先绑定 GitHub Actions；具体平台确定后挂接这些命令即可。依赖漏洞与许可证检查发现问题需记录处理结论，不能忽略后继续冻结镜像。

| 执行恢复 | 提交后丢消息、重复投递、worker 被杀、租约过期旧进程、Redis 重启及 LangGraph 写后恢复均不重复发布或创建任务 | 修复任务事务及恢复器，不能靠增加重试次数掩盖 |
| 数据与计算 | 真实脱敏报表可证明身份、粒度和覆盖；AC 样本计算有明确预期 | 明确不可用数据及降级，必要的业务口径变更交用户确认 |
| 模型与检索 | 指定服务及区域获确认，金标门槛达标，成本与时延有记录 | 修改提示或适配、比较候选模型；检索不足在冻结前决策 |
| 容量与恢复 | 目标 ASIN、SKU、记录量与并发实测；备份恢复能查回来源且符合约定目标 | 调整资源、索引或任务粒度，重新验证受影响项 |

不能凭一次 pip 安装成功宣称整套技术可用，也不能因为模型未选择而跳过其评测后直接发布。供应商具体候选需结合已授权区域、可用账号和预算决定；用户未提供这些条件时，只能冻结模型接口与业务约束，不能冻结服务商及产品最终验收。

### 11.12 已确认的自主调查架构与写入契约

**技术组合与选择理由**

采用 Python + LangGraph StateGraph + langgraph-checkpoint-postgres/PostgresSaver；图节点通过 HTTPX/Pydantic 模型适配器调用模型。Celery/Redis 负责后台分发，Django/DRF 负责入口、授权和业务命令，PostgreSQL 保存领域事实、审计及图检查点。单服务器以库方式运行 LangGraph，不额外部署 Agent Server 或强制依赖 LangSmith。LangGraph 和 checkpoint 包需一起锁定兼容版本，目前尚未完成安装和运行验证。

选择 LangGraph 的依据是 B43/B44 确实存在基于新证据的决策循环，需要显式条件边、持久状态及恢复。固定检查无需迁入图；LangChain create_agent 的通用循环不再叠加，供应商接入统一走已有适配器。允许依赖中出现 langchain-core 等底层包，不将“不采用 LangChain Agent”误写成禁止全部同生态依赖。

**入口与状态**

入口先执行 Authorize → ResolveScope → EnsureStandardChecks → StartInvestigation。ResolveScope 读取可见上下文、catalog 映射、该对象授权站点的异常摘要和覆盖。仅有一个可解释目标时自动定位；多个合理目标进入 needs_clarification，返回候选及依据。候选发现查询同样受权限过滤，不能显示未授权站点的名称或计数。显式指令与页面冲突不能静默覆盖。窗口采用需求默认规则并可见展示，不以模型推测填入任意时间。

EnsureStandardChecks 复用对象、窗口、来源和规则版本一致的标准报告，或调用现有固定服务完成。基础数据、标签作业不足时显示依赖等待及缺口；标签是否可用由覆盖规则判定。等待不占 worker，恢复时仍绑定既定输入版本；若用户选择最新数据，创建有父运行引用的新调查，不混用快照。

InvestigationRun 保存发起人、scope_id、对象及站点清单、指标与计量单位、窗口、snapshot_id、标准报告引用、workflow_version、model/prompt/schema 版本、预算、graph_thread_id 和状态。状态包括 queued、preparing、running、needs_clarification、waiting_data、completed、partial、cancelled、failed。调查是否完成与整改动作是否完成分开；存在待批准提案不代表调查进程必须一直运行。

LangGraph 状态保存已验证事实引用、探索假设、反证、已执行工具签名、未核查项、轮数及停止原因。工具审计表保存参数、结果摘要、数据来源、耗时和调用 ID；模型调用表保存实际尝试与 token 费用，预算账本是重放不能回退的权威记录。图内预算字段为镜像，恢复后重新读取账本。

**节点和工具**

循环为 Decide → ValidateDecision → ExecuteReadTools → RecordEvidence → CheckStop → Decide；结束分支为 ComposeResult → ValidateResult → PublishArtifacts。needs_clarification、waiting_data 和授权失效可从守卫节点退出。Decide 返回受限结构：tool_requests、finish 或 clarification，以及当前假设和简短选择理由。ValidateDecision 校验工具、对象、参数、粒度、权限及剩余预算；不允许模型生成任意代码或 SQL。

| 工具类别 | 输入输出契约 | 执行限制 |
|---|---|---|
| 对象与来源发现 | 解析目标及 scope → 站点映射、异常摘要、来源覆盖 | 入口 F 调用；需要扩展目标时返回澄清，模型不能自行增加授权范围 |
| 指标和分层比较 | 对象、指标、窗口、允许维度、snapshot → 分子分母、比较及覆盖 | 订单数、订单件数、成熟队列分别定义；维度白名单，不让模型算数 |
| 订单及退货核查 | 对象、过滤条件、分页 → 脱敏记录引用及生命周期事实 | 优先聚合；明细分页有总上限，不能以翻页绕过工具预算 |
| 评论主题与原文检索 | 对象、期间、主题或词语 → 分布或原文跨度 | 趋势使用完整有效标签；检索样本不冒充总体，无订单关联不自动认定同买家 |
| 运营事件及既有报告 | 对象、期间 → 事件、旧报告与版本引用 | 返回事实不证明因果；旧版本与当前快照差异必须说明 |
| 内部变更提案 | 对象、操作枚举、目标值、证据、实体版本 → 结构化提案 | 模型只能提出命令；权限、批准、执行由确定性服务处理 |

所有工具的 scope、snapshot 和执行身份由服务端注入，模型参数不得覆盖。每工具最多 100 条明细摘要或引用，截断返回 has_more 和覆盖信息；已知总量与取样数量分开。只读工具结果可按调用签名和快照复用；并行只用于无数据依赖的读操作，写操作顺序执行。

模型可以产生探索假设，不能改动标准候选排序；报告并列展示标准候选和探索线索。代码校验数字、引用存在性、引用范围、证据类型及可用性；这些校验不能证明自由文本的全部语义正确，因此固定事实使用模板，探索结论标注未证实并交业务评测，禁止自动升级为已确认因果。

**可写范围与提案执行**

PublishArtifacts 自动保存调查版本、证据关联和整改草案；可创建待核查任务，不能默认给它附上未经授权的责任人与截止日。AutoActionPolicy 保存规则 ID/版本、授权人、能力、scope、任务类型、负责人、期限策略、有效期和撤销状态。只有发起用户及执行身份都有相应能力且规则精确匹配，内部任务才可自动成为正式指派；缺少规则进入待确认状态。

ChangeProposal 保存 target_id、expected_version、before/after、evidence_refs、payload_hash、策略引用和 proposed/approved/rejected/expired/executing/succeeded/failed 状态。审批页面显示具体修改；审批人必须有执行权限，批准绑定精确版本。确认端点通过领域服务执行或投递唯一命令；运行时重新校验当前授权、策略有效性、目标版本和前置条件，冲突不自动重写提案后沿用旧批准。

每个命令使用 run_id + logical_action_id 幂等键，并额外按对象、任务类型和证据指纹关联既有未完成任务，避免新运行反复造待办。命令回执、业务修改、审计和提醒 Outbox 在同一事务提交；外层图在写入后崩溃，恢复先查回执，不重复执行。审计标识用户发起、Agent 提议、规则授权或人工批准，以及实际执行结果。只读调查也会保存这些内部产物，不能把“读工具白名单”理解为整个系统禁止写入。

Agent 不具备直接写数据库、修改导入事实或规则配置的工具。本次 Amazon/ERP 写入工具不注册；Listing、价格、库存及买家联系请求只能生成允许的草案或说明范围。任何外部业务执行能力需要单独的来源接口、操作授权及验收，不由内部任务批准推导。

**恢复停止与预算的唯一责任**

Job/Outbox 负责调度和运行级重试，Celery 领取运行后由 LangGraph 从 checkpoint 继续内部步骤；StepResult 仅驱动 L1，不同时恢复 L2 的节点。每个 graph_thread_id 对应一个调查运行，同运行禁止并发执行。工作进程持有该运行的数据库会话级 advisory lock，锁连接失效立即停止；checkpoint 写入使用该受控连接或包装器校验当前租约代数，不能让旧 worker 写入新运行状态。领域命令另外校验 fencing token，不把 checkpoint 原子性误当成业务写入原子性。

进程崩溃后锁释放，恢复器重新领取租约并加载图状态；挂起但仍持锁的进程须先终止确认退出才能接管，不能仅凭心跳过期就并行跑两份图。工具执行和 checkpoint 之间可重放，因此数据库命令必须有上述回执；模型已返回但未保存时无法保证供应商不重复计费，仍受持久尝试预算限制。

初始预算为 8 次模型决策、12 次只读工具调用、最多 5 个内部变更提案、300 秒累计主动执行时间；单次网络请求 30 秒、最多两次尝试。最终说明最多 1 次模型调用并计入整体时间/token/金额预算。执行前预留预算，执行后结算，重试、图恢复与分页不得重置；具体 token 和金额上限须待服务商选定后写入配置并验收。暂停等待人或数据不消耗主动执行时间，但保留已用预算；重新继续同一调查仍沿用累计额度，新的明确调查请求才可建立有链接的新运行。

强制停止条件包括预算耗尽、连续两轮无新增有效证据、重复调用同快照同参数、必要缺口阻断有效路径、用户取消及授权撤销。重复请求先复用缓存并提示该方向已查，不反复付费。取消后不再发起新调用或命令，正在返回的结果不得继续发布；已提交合法写入保留并展示，不作虚假回滚。安全线索立即走独立安全服务，不等待普通图结束，也不能借安全分支扩大数据权限。

权限恢复与补数继续必须重查当前授权和数据版本；权限撤销后停止并限制历史结果访问。流程升级后用兼容 workflow_version 恢复，不能用新节点语义解释旧 checkpoint；无法兼容则保留记录并在用户明确继续时创建新运行。

**实施和验收补充**

W-Agent 交付上述入口、图、工具、审计、预算和恢复；W4 交付命令授权与提案；W5 显示采用范围、数据截至时间、简短调查进度、待澄清、停止原因、实际写入结果和确认界面。均属本次同一交付。

AC-21 至 AC-26 必须覆盖：有唯一上下文无需追问、多站点同名需澄清、订单与件数区分、中间证据改变后工具路径改变、反证推翻假设、部分缺源仍可查其他方向、安全即时分流、模型超时、预算重启不清零、取消与撤权、写后崩溃不重复任务、旧版本批准拒绝。测试用可控模型响应验证机制，并用独立真实脱敏案例验证调查价值；不得仅以聊天回答自然流畅验收 Agent。实际案例的时效和可执行性沿用需求业务验收，技术故障与权限案例必须全部通过。

### 12.3 测试与发布关口

测试分为来源契约测试、指标已知答案测试、状态与并发测试、权限穿透测试、故障注入、固定语义检索评测和全流程验收。重点注入：发布提交后消息未投递、任务完成前进程退出、重复投递、扫描中来源更新、模型超时、两个用户同时关闭事件及备份恢复后的任务补跑。

完整功能完成后进行不少于 3 周的影子运行，覆盖至少 2 名运营、10 个真实子 ASIN、30 个核查事件。沿用需求的调查用时降低至少 30%、可执行报告至少 60%、一般无效告警不高于 20% 门槛；样本不足延长或分列真实历史回放结果。影子运行是完整产品验收，不是缩小范围的试用版交付。
