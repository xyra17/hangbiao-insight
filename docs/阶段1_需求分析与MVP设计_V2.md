# 商品经营异常分诊与证据审计

需求分析与开发范围冻结基线 V2

修订日期：2026-09-20。本文定义亚马逊商品经营异常排查系统的一次性交付范围、统计口径、处理流程和验收标准，供产品、运营、开发与测试共同使用。所有纳入范围的需求均属于同一次交付；开发工作包只表达依赖关系，不代表分期发布。

文件名保留历史命名以兼容现有链接。Markdown 为需求维护源，Word 为同内容阅读稿。本文取代此前的 MVP 优先级表、分版本路线和相冲突的开发规格；已有代码与历史验收记录仅描述实现现状，不能替代本次验收。

## 1 产品定位与业务边界

系统帮助商品负责人发现值得处理的异常，核查经营事实，汇集不同报表与反馈中的证据，形成有边界的原因候选，并把调查、处理和复查记录在同一事件中。

一句话交付：每天看到需要处理的商品事件，知道发生了什么、哪些因素已有证据、哪些尚未核查、由谁做什么，以及何时判断处理是否有效。

### 1.1 覆盖的业务问题

- 销量或转化指标下降：先核查可售状态、购物车占比、可售库存、流量、价格和促销，再检查体验反馈是否有解释力。
- 退货退款增加：区分当期发生量和同批销售订单的后续表现，定位问题子体、原因类型与可验证的批次线索。
- 页面评分或反馈结构变化：区分页面星级、采集评论均分与主题变化，判断是否值得处理及应核查的对象。
- 严重产品安全反馈：单独进入人工核查，不等待经营指标异常或统计样本达标。
- 标准检查后的自主调查：运营可用模糊自然语言要求分析异常；系统在授权范围定位站点、商品和窗口，核查指标、订单与评论，依据新证据继续调查。
- 处理结果复查：记录修改、抽检、补货等动作及其生效时间，观察后续可比数据，避免重复排查。

### 1.2 与现有后台的关系

Amazon Voice of the Customer 已提供客户体验健康度、常见问题与处理建议。系统的价值应体现在跨报表核查、子体定位、证据追溯和处理跟进，而不是重复生成客户问题摘要。验收基线是运营当前使用 Seller Central、ERP 和 Excel 的实际流程。[来源 S4]

本系统不承诺确定因果或替代运营决策。候选排名仅表示“在已核查范围内，优先调查哪些解释”，不能把未接入因素视为已排除。

### 1.3 明确不交付的能力

广告投放优化及广告归因、竞品爬取与竞争归因、跨商品全局因果分析、利润核算与赔偿索赔系统、动态多 Agent 调查、无人确认的调价／改 Listing／停售／移除库存、向买家发送消息、诱导修改评论，均不属于本次范围。系统可记录运营提供的广告调整事实，但不能据此编造广告效果结论。

不以未来版本承诺填补本范围的闭环。外部平台 API 自动授权连接、企业微信／邮件推送与向 ERP 写回也不属于交付门槛；数据导入、站内待办、人工分派、报告导出和复查必须完整交付。

## 2 目标用户与权限

主用户是对一组商品负责的亚马逊运营／商品负责人。商品归属可以覆盖多个店铺、站点和履约方式，但每次诊断在明确对象内完成，跨站点不直接混算。

| 角色 | 必须能完成的工作 | 权限边界 |
|---|---|---|
| 商品负责人 | 查看队列、核查证据、确认或驳回候选、创建动作、分派和复查 | 仅访问授权店铺与商品，可关闭所负责事件 |
| 品控或供应链负责人 | 查看问题样本、核对实物／包装／批次、上传处理结果 | 处理被分派任务，不改写原始经营数据 |
| 售后负责人 | 核对退货退款、关联工单、补充客户问题事实 | 仅访问获授权记录，原始记录修正通过新数据版本完成 |
| 数据管理员 | 配置数据映射、商品映射、阈值、成员和数据源 | 配置变更有版本和审计记录 |

小团队允许一人兼任多角色，不强制存在独立客服或品控团队。商品必须配置默认负责人；未配置时进入管理员的“未分派”队列，不能静默丢失。单机模式使用本地默认管理员且仅监听本机；供多人访问时必须启用登录、角色权限和店铺隔离。

## 3 用户问题与价值验证

以下是待用真实案例验证的业务假设，不把现有程序缺陷表述成已证实的用户痛点。

| 业务假设 | 典型工作损耗 | 需要保存的验证记录 |
|---|---|---|
| 跨来源核对耗时 | 下载报表、对齐日期、定位订单和子体、翻看原文 | 当前调查步骤、人工用时、系统辅助用时 |
| 指标变化容易被误读 | 当期退款错除当期销量、父体混算、缺数据当零 | 原判断、核查事实、纠正后的判断 |
| 告警多但优先级不清 | 一个问题多个告警、已知促销变化重复提示 | 每日告警量、合并率、无效打扰原因 |
| 处理后没有复查依据 | 修改页面或包装后，没有记录生效时间和观察窗口 | 动作、完成日期、观察订单范围、复查结果 |

数据上传、映射和补录时间计入使用成本。系统节省的查数时间若被日常准备数据的时间抵消，不视为业务成功。影子运行用于验收完整产品及校准已定义参数，不用于把核心功能推给下一次交付。

## 4 产品原则

1. 先确认事实、口径与数据完整性，再做候选解释。数据延迟、缺失和业务零值分别表达。
2. 数值计算、检测规则、标准候选生成和排序由确定性代码执行；LLM 负责语义抽取、问题解析和有引用的叙述。自主调查允许模型选择下一步工具并提出探索假设；探索线索与规则候选分列，不改写统计口径，不自动宣布因果成立。
3. 每项结论可回到原始行或原文，记录对象、窗口、数据版本及计算规则。支持证据、反向证据和未核查项同时展示。
4. 不将客户选择的退货原因直接视为已确认根因，不将同时发生视为因果，不将“无反馈”当作质量良好的证明。
5. 证据可信度和业务紧急度分开。严重安全线索可立即要求人工核查，但不能因此判定缺陷普遍存在。
6. 数据不足时仍提供具体核查任务；不能以强行补齐原因、金额或置信度制造完整报告。
7. 经营异常、体验问题、数据质量问题分开管理；一个业务问题尽量只有一个持续跟进的事件。

## 5 执行方式与交互范围

### 5.1 查询、标准检查与自主调查

系统采用 L0 查询、L1 标准检查和 L2 自主调查。简单语义任务单 prompt 完成；步骤可定义的任务采用预定义流程及条件分支；下一步依赖新证据、需模型自主选择工具的调查进入 L2。L1 覆盖销量、转化、退款、评分和安全检查，L2 使用单个有界 Agent，属于本次完整交付，不采用动态多 Agent 协作。

统一流程：数据导入或更新 → 完整性检查 → 指标计算 → 异常检测 → 事件合并 → 按场景取证 → 候选排序 → 人工核查与处理 → 到期复查。

### 5.2 自然语言入口

自然语言入口支持查指标、比较窗口、检索反馈、查看候选依据、缺失数据和处理状态，以及“检查这个商品为什么退货增加”等自主调查请求。先识别查询或调查意图；能单次查询回答的不启动 Agent，调查请求由系统衔接 L1 与 L2，用户无需选择技术模式。

已有页面和事件上下文可以继承，必须可见；先按第 5.3 节自动定位可确定的对象，仅在授权范围内仍有无法消除的歧义时要求选择。中文和英文商品名、ASIN／SKU、常用缩写应有路由测试。超出范围时解释可支持的调查方式，不猜测对象，不触发外部业务动作。

LLM 不可用时，队列、统计、规则报告、证据检索和处理闭环仍可使用；自然语言解析降级为筛选控件，自主调查标记暂停或部分完成，不把规则报告冒称自主调查完成。尚未完成的语义标注明确显示覆盖率，不能用少量已标注评论冒充完整窗口。

### 5.3 自主调查与模糊指令定位

2026-09-20 用户确认：系统同时承担标准检查后继续自主调查的职责，允许自动保存调查产物及执行明确授权的内部任务；有界不等于只读。该确认纳入本次交付范围。

例如“看看这个商品最近订单怎么掉了”：优先使用明确问句、当前事件、页面已选商品及期间；显式输入与页面范围冲突时展示差异并确认切换。缺少站点时，可以查询当前授权工作区内该商品的站点映射、异常摘要及来源覆盖，不能只因信息未写全就立即追问，也不能搜遍无关店铺。只有唯一匹配或上下文唯一定位时自动继续，展示采用的对象和依据。多个合理候选则列出站点、指标变化和数据日期供选择，不能仅按最大跌幅擅自认定用户所指。

“最近”优先沿用事件窗口或可见筛选窗口，否则采用第 8 节对应指标的默认窗口及共同完整截止日，并明确展示。订单数使用订单口径，不能用销量件数替代。用户明确要求跨授权站点比较时逐站点分析并列展示，不混算币种、时区或分母。对象无法确定时只做定位查询，不进行业务写入。

定位后加载同输入版本的标准检查；无有效检查时自动执行 L1，无需用户先手动运行。L2 必须能根据工具返回自主选择细分子体、履约方式、时间段、订单队列、主题及反证查询；不能仅把固定步骤包装成聊天。数据缺口不等于全部停止：仍有可验证方向就继续，只有关键缺口阻断剩余有效路径时停止并形成补数任务。

每轮保留所选工具、参数、选择依据的简短说明、输入版本、结果引用、假设支持与反证；不要求记录模型私有思维链。探索线索必须有证据引用和可验证方式，未验证的假设不得变为已确认原因。遇到严重安全线索立即进入既有安全核查流程，不等待普通调查结束。

初始上限为每次调查 8 次模型决策、12 次只读工具调用、300 秒主动运行时间；另有工作区 token、费用与并发预算，具体模型确定后填入数值。基础 L1 和新增标签作业分别计量并在界面展示等待，不消耗 Agent 循环预算；不得以拆子任务绕过总成本限制。连续两轮无新有效证据、重复查询、必要数据不可得、预算耗尽、用户取消或授权失效时停止，区分已完成、部分完成、待澄清、待补数据、已取消和失败。上限是验证初值，非无限调查承诺；等待用户不占 worker。

### 5.4 主动写入与执行权限

| 操作等级 | 本次处理方式 | 必须满足的条件 |
|---|---|---|
| 调查产物 | 自动保存调查记录、证据关联、版本化结果、整改草案及待核查任务 | 对象已确定、具备创建权限、引用有效、幂等去重；待核查任务不等同正式整改承诺 |
| 已授权内部任务 | 按预先配置的规则自动创建或指派内部核查任务 | 规则限定工作区、对象、任务类型、负责人和期限策略；记录授权规则版本，未匹配不能由模型猜测授权 |
| 业务承诺或结论变更 | 采纳建议、无预授权指派、修改既有期限、关闭事件等先形成变更提案，再由有权用户确认 | 展示对象、原值、新值、依据和影响；执行前重查权限、实体版本及前置条件 |
| 外部经营变更 | 可以形成调价、Listing 或库存处置草案及人工执行记录，本次不自动写入 Amazon 或 ERP | 当前报表接入不含外部写接口；将来接入前按操作逐类制定权限和确认规则，不因本次授权自动开放 |

所有写入经过业务命令接口，模型不能直接改表。一次用户确认只授权该版本提案，参数改变需重新确认；模型文字、评论原文、角色名称不能替代授权。调查失败或取消不会抹掉已合法保存的记录，界面显示实际已写入内容；未执行提案不伪装成成功。审计包含发起用户、Agent/规则执行身份、授权依据、输入输出、实际变化及执行结果。

## 6 运营工作流与报告

### 6.1 每日工作入口

默认在工作空间时区每日 08:00 扫描已导入数据，可配置时间。成功导入后也可触发扫描；手动和定时扫描使用同一规则与幂等机制。按站点本地日期计算业务窗口，时间显示包含时区。

队列展示事件而非孤立指标，按紧急程度、影响与待处理时间排序。每条至少包括对象、问题摘要、发生时间、数据截至时间、变化幅度、影响规模、证据状态、负责人、下一步动作及处理状态。支持“新发现、恶化、待我处理、待补数据、待复查、已关闭”筛选。

定时任务运行不等于数据已更新。无新数据不得重复生成“今日新异常”；失败或过期数据进入数据源待办，并保留最后有效结果及其时间。

### 6.2 调查顺序

| 场景 | 必查顺序 | 不能输出的结论 |
|---|---|---|
| 销量下降 | 数据完整性 → 可售状态／购物车 → 可售库存 → Sessions → Unit Session Percentage → 价格促销／运营事件 → 体验反馈 | 缺流量或可售状态时认定评论是销量下降主因 |
| 转化指标下降 | 分子分母及聚合口径 → 子体组合 → 购物车／库存 → 到手价可得事实／促销 → 页面变更与反馈 | 将销量下降本身作为转化下降证据 |
| 退货退款增加 | 当期发生与销售队列口径 → 原因数量和占比 → 子体／履约 → 处置状态和工单 → 可关联批次／运营变更 | 将买家选项、仓库退回和退款金额当成同一事实 |
| 评分或评论变化 | 页面快照与采集完整性 → 变体归属 → 同主题极性及样本 → 退款工单对照 | 从采集评论均分推算页面星级 |
| 严重安全反馈 | 回查原文及否定语境 → 确认对象 → 立即分派人工核查 | 低样本直接忽略，或未经核实宣告缺陷成立 |

### 6.3 报告固定内容

报告按“发生了什么 → 已核查什么 → 候选解释及限制 → 该做什么”的顺序展示。必须包含指标口径与样本、基线和当前窗口、子体分布、数据覆盖和延迟、支持／反向／冲突证据、未核查维度、候选排序依据、影响金额或订单规模、负责人和复查安排。

候选允许为空、并列或相互冲突，不要求凑满 Top 3。使用“已核实的事件”“有支持的调查方向”“待验证线索”三级表达，不展示未经校准的原因概率。详情可展开原始记录、计算过程与历史报告版本。

下表所有 FR 均为本次交付和验收范围，不设置按版本推迟的核心功能。某个数据源在某商家处缺失，不等于对应功能不需要实现。

## 8 数据需求与统计口径

### 8.1 商品身份与关联

业务分析键为 shop_id + marketplace_id + child_asin + seller_sku + fulfillment_channel，内部 product_id 为该对象的代理键。父 ASIN 用于导航和聚合；同一 ASIN 多 SKU 不得复制一份 ASIN 流量到每个 SKU 后再相加。

每个来源保留 native_grain 和 reporting_scope。只有来源本身提供的粒度才可计算；缺 SKU 的 ASIN 级报表在 ASIN 层分析，并标注履约不可拆分，禁止按销量随意摊分。商品映射记录生效时间；父子关系调整、合并或拆分前后不能无说明地拼接趋势。

订单／订单行／商品身份用于关联退货、退款与工单。batch_no 仅在存在订单行到实物批次的可靠映射时参与批次结论；没有映射时显示“批次未关联”。评论通常仅关联商品，不默认关联订单、买家或生产批次。

### 8.2 数据源与接入责任

统一交付 CSV 文件上传和本地目录定时批量导入，支持预览后保存映射模板；不要求人工逐行重录。目录接入配置已授权路径、文件模式、来源类型和扫描频率（默认每日扫描前一次）。文件缺失、格式改变和校验失败有数据源告警。

外部 API 自动连接不作为本次依赖。Amazon／ERP 原始导出字段通过适配器映射；不假设所有账号、站点具备相同接口或权限。评论由商家提供的有权使用的数据集或授权来源导入，不承诺 SP-API 可提供完整评论原文。

| 数据域 | 最低可用数据与提供者 | 建议更新与缺失行为 |
|---|---|---|
| 商品与负责人 | 商品映射表，由运营／管理员维护 | 有变更即更新；映射不明的记录隔离待处理 |
| 销售与流量 | Business Reports／ERP；日期、原生粒度、件数、订单口径、Sessions、购物车占比 | 按日导入；没有流量不解释转化，没有销售基数不算率 |
| 订单或发货明细 | ERP／订单与发货报表；订单行、日期、件数、商品、履约 | 按日；缺明细仅支持发生口径，不支持销售队列率 |
| 退款交易 | 财务／ERP；交易 ID、订单行、时间、金额、币种，件数若来源提供 | 按日；金额不能倒推退款件数，退款撤销保留冲正 |
| 退货记录 | FBA 退货报表／FBM 退货导出；记录 ID、订单、件数、原因、状态及日期语义 | 按日；申请、收到和退款分开，不将收到日当申请日 |
| 工单及客户反馈 | 卖家可获得的客服记录；工单 ID、时间、问题、状态及可选订单 | 按日或批次；不要求 FBA 商家提供完整平台客服记录 |
| 库存和可售状态 | 库存报表／ERP／运营核查；可售、预留、在途、不可售和状态快照 | 按日；只有总库存不得推出可售或可售天数 |
| 价格和促销 | 价格／促销导出或运营表；生效起止、标价、折扣机制、币种 | 有变更即更新；未知到手价不得用标价替代 |
| 评论和页面星级 | 授权评论文件及页面快照；原文、评分、评论时间、采集时间、变体、语言 | 按日或批次；显示采集范围，不把未采集解释为零评论 |
| 运营事件与批次 | 运营／供应链记录；改图、文案、包装、供应商、补货、计划促销等 | 发生即登记；人工事实标来源、登记人和有效时间 |
| 平台问题提示 | 可获得的 VoC／可售异常记录或人工核查附件 | 有变化即更新；无来源时列为待核查，不推断账号处罚 |

FBA Returns 报告记录仓库收到的退回商品，包含原因及处置等字段，不能替代完整退款交易账。[来源 S2] Sales and Traffic 报表可提供销量、流量及购物车相关指标，适配时仍须保留报告请求窗口和原生聚合层级。[来源 S1]

### 8.3 数据完整性与时间

每次导入记录 source_id、source_file_hash、report_type、报表范围、native_grain、生成时间、导入时间、数据截至时间、完整性声明、映射版本和行号。金额保留币种；站点间不直接合计金额，未提供汇率时不显示跨币种总额。

状态统一为 ready（窗口完整）、partial（局部覆盖）、stale（过期）、missing（无源）、invalid（校验失败）。零值仅在完整报表明确为零，或其报表契约允许将缺行认定为零时成立；其他缺行保持未知。部分数据可以展示事实，不参与需要完整分母的异常计算。

日源默认数据截至时间落后站点当前日期超过 2 天视为 stale，可按来源延迟配置。比较窗口截止日为该项计算所需日源共同的最新完整日 D，不包含进行中的当天；不得把不同截至日的指标强行放在同一窗口。独立的严重安全反馈按最新导入立即核查，不被共同截止日拖延。

窗口使用站点本地日历日，包含起止日；时间戳内部保留时区并可换算 UTC。历史月表只用于月度复盘，不能拆成假日数据或作为每日告警验收依据。月表仅比较完整月份，趋势展示区间与检测窗口分开配置。

近 90 天数据在每次更新时允许回补重算，更早修正通过指定区间重算；保留旧报告，不覆盖已据此采取的动作。相同业务记录重复导入只更新来源版本，不重复计数；退货状态流转更新同一退货记录，不把申请和收到各计一次；同订单不同退货行保留唯一业务键。有效退款按同一交易链截至计算时点的净退款金额大于零判定，换货单标记与原单关联且不重复计为原始销售。退款冲正、评论修改和删除标记按来源可确认状态处理，不因本次文件未含历史记录就自动删除。

### 8.4 指标定义

| 指标 | 冻结口径 | 限制 |
|---|---|---|
| 订单量与销量 | order_count 为来源明确的去重订单数；units_ordered 为订购件数；shipped_units 为已发货件数 | 订单、订单行、件数分列，不用同一字段互换 |
| 销售额 | 按来源币种和税费／折扣范围保存金额 | 不称为利润或净损失 |
| Sessions | 同一来源、原生对象、日期的会话数 | 无更细分数据时不摊到 SKU 或履约方式 |
| Unit Session Percentage | units_ordered ÷ sessions × 100%，跨日先合计分子分母再计算 | 中文标注“件数／会话转化指标”，不是购买用户概率，可超过 100% |
| 购物车占比 | 保留来源 buyBoxPercentage／Featured Offer 指标及口径 | 跨期仅在权重匹配时加权；无权重只展示原始日值和日均描述，不冒充平台期间值 |
| 当期退货／退款发生量 | 按各自事件日期统计件数、交易数与退款金额 | 不除以当期销量并解释为产品缺陷率 |
| 30 天销售队列退款订单率 | 已发货订单按首次发货日分组；30 日内存在有效退款的去重订单数 ÷ 该组已发货订单数 | 按商品对象去重订单；部分金额退款计一次，不能推断整单件数均有缺陷 |
| 30 天销售队列退货订单率 | 同类订单分组，30 日内出现同一种退货事件的订单数 ÷ 该组订单数 | 申请／仓库收到二选一按源固定，名称显式说明，不混用 |
| 退货原因占比 | 特定退货事件口径下，该原因件数 ÷ 全部退货件数 | 展示未知原因；多原因标签另标口径，不能假定各项相加为 100% |
| 页面星级与评论均分 | 页面星级保存快照；评论均分仅对实际采集到的窗口评论计算 | 两者不互相推算；Amazon 页面星级非简单算术平均 [来源 S3] |
| 主题负向提及占比 | 提及该主题且为 negative／mixed 的去重评论数 ÷ 同窗口已完成语义分析的有效评论数 | negative 和 mixed 分开可查；同评论同主题计一次，不等于订单缺陷率 |

分母为零显示“不适用”，无分母显示“缺失”；基线为零不输出无穷大增长率，仅输出新增数量和差值。缺失分子分母的外部比率只能展示为来源报告值，不能用于置信区间、跨窗加权和队列率验收。

30 天是产品用于可比分析的默认观察期，不代表 Amazon 退货政策期限。观察期从该分析对象订单的首次发货时间起算，默认区间为 [首次发货时间，首次发货时间 + 30 天)，按时间戳判定；仅有日期时统一以站点当日 00:00 作为时间精度约定并标注。观察期可按品类配置为其他天数，但同一比较内必须一致。一个订单完整观察期到期且退款／退货来源覆盖该期间才算成熟；新近订单明确标记“观察未完成”，不得与成熟订单直接比较。延迟发生的退款另列，不回填成 30 天内发生。

例：上月售出 1,000 件，本月售出 200 件，本月发生 30 件退款；只能说明本月发生量，不能以 15% 判定本月产品质量。必须先确定退款对应订单和发货时间。

### 8.5 评论与反馈分析

保留 review_id、ASIN／已知变体、原文、星级、语言、评论时间、采集时间、已购／Vine 等来源可得标记、原始引用和修改版本。未知标记保持未知，不擅自剔除非已购或 Vine 评论。

中文和英文纳入语义验收。其他语言原文可存储和检索，显示“未完成语义支持”，不悄悄计入已分析分母。翻译仅辅助阅读，原文始终可回查。

固定主题词表覆盖功能、耐用性、安全、尺寸适配、安装使用、配件缺失、描述不符、包装破损、配送及价格感知，并允许 unknown。每个主题独立标 positive／neutral／mixed／negative，保存原文片段和分类器版本；星级不得直接替代文本极性。

每窗同时展示采集数、有效数、完成标注数、主题数量和占比。标注覆盖率低于 90% 时只描述已分析样本，不触发主题趋势告警；即使达到阈值，也不能声称覆盖全部买家。关键词检索提供同义词和中英文词表，统计不得只用检索到的 Top K 评论计算。

同一买家的工单、退货和评论若可通过合法可靠的订单关联识别，应作为同一经历处理；仅凭相似措辞不能强行关联。不可关联时分别报各来源数量，不相加为独立受影响订单。

反向证据必须匹配主题、对象和时期。“外观满意”不能反驳“断电问题”；没有差评不自动构成反向证据。退款原因“有缺陷”与评论主题“断电”相互支持时，仍不能跳过实物核验就确认生产缺陷。

### 8.6 运营事件表

至少记录 event_id、对象范围、event_type、有效起止、变更前后内容、登记人、登记时间、依据附件或记录引用。支持页面修改、促销开始／结束、调价、供应商／包装变化、补货与计划清库存。

事件重叠仅生成调查线索。系统展示时间对齐情况，不自动宣称“排除了季节、大促、生命周期”。已知事件可以解释和暂缓一般告警，但不自动压制安全反馈。

## 9 异常检测与事件管理

### 9.1 窗口与统计规则

日常经营默认当前窗口为截至 D 的最近 7 个完整日，基线为此前 28 个完整日；数量按日均归一，两个窗口均覆盖整周。评论默认最近 28 日对前 28 日；低样本时双方等长扩展到 56 日，仍不足则只提示观察。销售队列默认最近 28 个已成熟的发货日对前 28 个已成熟发货日。

新品缺足够历史时显示“基线不足”，保留绝对状态检查及严重反馈核查。同比只在历史充足且对象和来源可比时作为辅助，不作为所有商品的强制条件。大促、变体重组、补货和价格变更重叠时标记基线可比性受限，不自动断言已去除影响。

二项占比提供 95% Wilson 区间；两个独立窗口的占比差使用基于 Wilson 区间的 Newcombe 方法。只有差值区间不跨 0，才可使用“样本内统计差异”措辞，仍不代表因果或消除采样偏差。多主题同批扫描若使用显著性标签，对各主题的两窗计数做双侧 Fisher 精确检验，再按同一对象、同次扫描的全部主题做 BH 校正，q ≤ 0.05。只有差值区间和校正结果同时满足条件才显示该标签。

Unit Session Percentage 不是二项概率，不套用二项区间；件数、金额和页面星级也不机械套用占比公式。样本小可提示待观察，不能统一阻断严重事件。

### 9.2 冻结的默认检测配置

以下为可配置的产品默认值，用于启动和可复现验收，不宣称是 Amazon 行业阈值。参数更改须有配置版本、原因和影响预览；发布前可以通过影子运行校准，不改变指标定义。

| 信号 | 默认触发条件 | 结果 |
|---|---|---|
| 销量下降／激增 | 7 日日均相对基线变化至少 30%，7 日实际件数与基线预期差至少 10 件，基线 28 日至少 40 件 | 创建经营核查事件；激增且无风险默认观察级 |
| 流量下降 | Sessions 日均下降至少 30%，基线至少 200 Sessions | 作为流量调查方向，不能解释广告或竞品原因 |
| 转化指标下降 | 双窗口各至少 100 Sessions，Unit Session Percentage 相对下降至少 20% 且绝对下降至少 2 个百分点 | 创建／关联转化事件，不标因果 |
| 成熟队列退货／退款率 | 两窗各至少 100 个成熟订单，当前相关订单至少 5 个，升幅至少 2 个百分点且差值区间下界大于 0 | 创建体验风险事件；样本不足则显示观察线索 |
| 当期退货退款突增 | 7 日日均事件数较基线日均增加至少 50%，7 日累计较基线预期增量至少 5；零基线则当前至少 5 | 创建发生量核查事件，不称质量恶化 |
| 页面星级下降 | 同一展示对象两个有效快照间下降至少 0.2 星，最近对照快照不超过 7 日 | 核查页面和评论范围变化，不由评论均分解释 |
| 主题负向变化 | 两窗各至少 30 条已分析评论、覆盖率各至少 90%，当前主题负向及混合至少 5 条，占比增加至少 10 个百分点 | 创建反馈趋势线索，显著性另按第 9.1 节判定 |
| 可售／库存／购物车异常 | 新的不可售状态；可售库存由正转零；同口径购物车占比连续两个完整日低于 80% 且较基线日均下降至少 20 个百分点 | 可售／断货即时核查，购物车为核查线索 |
| 严重安全反馈 | 任一新记录包含实际起火、冒烟、伤害等疑似经历，经规则或语义检测标记 | 最高紧急度人工核查，保留否定和假设语境，不宣称已证实 |

普通指标须连续两次包含新增完整日数据的扫描仍满足条件才标记“持续”；首次满足即建事件，不用第二次扫描拖延首报。连续扫描没有新数据只保留状态，不计新的趋势证据。评论量骤减先检查采集完整性，不自动升级为经营异常。

### 9.3 合并与优先级

异常记录键包含分析对象、指标、窗口、规则版本和数据版本；同次扫描幂等。开放事件按对象和问题族合并（销售／转化、退货退款／体验、可售／库存、安全），新增指标或窗口追加证据。同一对象不同问题族互相链接，不因时间接近强行认定同一原因；人工可合并／拆分并留痕。父体聚合只作汇总，不抹去子体异常。

队列先按紧急度排序：紧急（安全、已确认不可售或断货）、高（满足成熟队列风险或销量下降条件）、普通（其他可行动信号）、观察（低样本及无伴随风险增长）。相同级别按超阈值比例、影响订单／件数、持续天数、首次发现时间稳定排序。未知影响量排在同级有已知影响的事件之后，但不降低安全紧急度。

当期退款金额称“退款金额”，不能直接称净损失；预期少售件数只作基线偏离，不换算确定损失。没有成本和费用数据不展示利润损失估计。

### 9.4 状态与提醒

状态为待核查、处理中、待观察、已关闭；另有待补数据标记和暂缓到期时间。确认／驳回针对某个候选，不能等同于关闭整个事件。

- 待核查 → 处理中：负责人接手或分派有效动作。
- 处理中 → 待观察：动作已完成，已填写生效日期、观察指标与复查日期。
- 任一开放状态 → 已关闭：负责人选择已解决、误报、已知变化或重复，并填写依据；未解决风险不能仅因“已分派”关闭。
- 已关闭事件在 30 日内同对象同问题族再次触发时重新打开并关联原动作；超过 30 日建新事件并链接历史。
- 暂缓不改变证据和状态；到期、紧急度升高或新安全线索出现时解除。普通新增证据更新事件，不重复通知。

站内仅对新事件、明显恶化、重新打开、任务分派和复查逾期生成待办。“明显恶化”指紧急度升级，或同口径异常偏离幅度相对上次已通知值增加至少 25% 且仍满足原触发条件；新增严重安全线索始终提醒。同类通知按事件与数据版本去重。安全事件不得自动暂缓或自动关闭。

## 10 证据与候选解释

### 10.1 EvidenceFact 契约

每项事实必须有 fact_id、source_type、analysis_scope、native_grain、window_start／end、data_as_of、coverage_status、fact_type、source_refs、data_version 和 rule_version。source_refs 至少包含导入批次与原始行号，或可回查的原始记录 ID；在线链接仅作辅助。

统计事实另含 numerator、denominator、unit、baseline_value、current_value、delta、sample_size、样本单位、confidence_interval 和方法。状态／变更事件另含 occurred_at、before／after、event_status；这类事实的 sample_size 可以不适用，不为满足 schema 伪造样本数。

文本证据另含 source_record_id、原文片段及位置、语言、topic、polarity、classifier_version、人工复核状态。MissingSignal 单独包含缺失源、影响哪些判断、提供者、所需字段和日期范围，不伪装成零值 EvidenceFact。

### 10.2 候选生成与稳定排序

候选由规则生成，包含候选 ID、问题族、必要条件、支持事实、反向事实、冲突事实、缺失检查项与建议核查动作。允许并行存在多个因素，允许没有符合条件的候选。

| 候选方向 | 最低支持条件 | 必须保留的限制 |
|---|---|---|
| 可售或库存阻碍 | 可信状态／库存变化与异常时间重叠 | 库存快照不能证明精确断货小时数 |
| 购物车或流量变化 | 同对象同口径的购物车或 Sessions 变化 | 不自行扩展成广告、排名或竞品根因 |
| 价格促销变化 | 有生效日期的价格／促销事实与经营变化 | 到手价未知、客户构成变化等仍需核查 |
| 描述或适配问题 | 同子体相关反馈增加，并有页面／规格核查事实或明确待查项 | 买家“不合适”不直接证明描述错误 |
| 产品或包装问题 | 同主题退货／工单／评论线索，附数量和关联限制 | 确认缺陷需人工核验；定位批次需可靠批次映射 |
| 子体组合变化 | 整体率变化且可比子体分层结果／销售权重可计算 | 数据不足时只提示检查结构，不补造分解值 |
| 数据异常 | 缺报、重复、日期错误、来源冲突或映射变更 | 进入数据任务，不作为经营根因对外陈述 |

排序依次比较：核实状态（人工核实事实优先）、对象与时间匹配程度、证据完整性、独立来源支持程度、未解决反证数量，最后以稳定候选 ID 打破并列。同一经历的多条记录不能提高独立来源支持分；无法关联的来源可显示交叉一致，但独立性记为未知。不得把自定义分数包装成概率。

在标准报告中，LLM 不改变规则排名、不增删规则候选、不补数字，只解释已校验事实；L2 可另行提出有引用的探索线索，不能伪装成规则候选或已确认原因。Evidence Guard 同时校验引用存在、对象与窗口匹配、数值一致、证据类型及缺失限制是否保留；自由叙述的证据支持程度另经固定案例及人工评测，不宣称仅靠规则可证明语义正确。校验失败降级为规则报告，保留失败原因。

### 10.3 人工判断与审计

原始事实、系统候选和人工结论分开保存。人工可确认／驳回／调整处理顺序，必须记录原因与依据；人工确认不自动成为模型训练真值。新数据推翻旧判断时生成新报告版本，提示负责人复核，保留旧判断和动作时间线。

## 11 动作分派与效果复查

每个正式 Action 至少包含 action_id、event_id、owner、动作类型、目标对象、依据引用、待验证问题、完成条件、到期日、状态、实际完成日、业务生效日、结果记录、观察指标和复查日。调查草稿及待核查任务可暂缺负责人和到期日；转为正式 Action 时须补齐并通过第 5.4 节的授权检查。完成及结果字段按状态填写，不预填虚构结果。

| 问题线索 | 可执行动作 | 完成和复查依据 |
|---|---|---|
| 尺寸不符增加 | 运营核对指定子体尺寸图／单位；品控抽测实物 | 保存核查结果；确认错误后记录修改生效日；复查相关成熟销售队列 |
| 包装破损增加 | 核查退货处置、包装照片与可关联发货批次 | 保存抽检结论和包装变更；观察生效后相同口径反馈 |
| 销量下滑且库存为零 | 核查可售状态、补货日期、预留与在途数量 | 记录恢复可售时间；复查库存与销量，不能归因评论 |
| 促销结束后销量下降 | 确认计划事件并与可比非促销窗口核对 | 确认已知变化，可暂缓；异常超出解释范围时继续调查 |
| 严重安全线索 | 指派商品负责人和品控核对原文、实物与涉及范围 | 保存人工风险判断及后续处置；任何外部操作由授权人员执行 |

复查默认经营指标在动作生效后满 7 个完整日进行；需要成熟队列的退货退款在观察期到期且数据完整后复查。采样不足可以延长并填写原因。观察报告分别显示“动作完成”“指标改善”“因果未证实”，并列出期间促销、流量等其他变化。

## 12 页面与交互要求

工作台包括事件队列、调查报告、处理与复查、商品映射、数据源管理五个主要页面，报告内嵌反馈检索和自然语言调查入口，展示定位范围、调查进度、已查工具、停止原因及待确认提案，不另建必须依赖聊天的工作入口。

- 队列默认展示前 20 个待办，分页可见全部；“前 N”只控制展示，不丢弃事件。
- 报告首屏回答对象、异常、影响、数据限制和下一步；详细统计与原文按需展开。
- 数据源页面展示所需数据、可用范围、过期原因、错误行、待补字段和负责人，支持下载模板及复用映射。
- 分派、关闭和暂缓操作显示结果并持久化；失败不伪装成功，刷新后状态一致。
- 当前周期、站点、币种、样本单位和模拟数据标识不能隐藏；无数据使用空态和下一步指引。
- CSV 导出按权限过滤并防止公式注入；报告导出保留数据截至时间、版本、引用和缺失限制。

## 13 非功能要求

| 维度 | 冻结要求 |
|---|---|
| 可复现 | 同一数据、规则、映射和语义标签版本的指标、标准候选及其排序一致；LLM 文案与探索假设单独版本化，自主调查保留调用及证据轨迹，不承诺模型重复运行路径一致 |
| 性能基线 | 在 8 核 CPU、16 GB 内存、SSD 条件下，按最多 1,000 个子 ASIN、3–10 名用户、180 天日数据和至少 10 万条反馈／交易记录验收，记录 SKU 展开规模并验证 10 人并发；缓存队列与报告查询 P95 ≤ 3 秒，已有语义标签的全量扫描 ≤ 15 分钟 |
| 长任务 | 导入、语义标注、重算显示进度和错误，可恢复；报告不等待外部模型才能展示事实 |
| 模型降级 | 单次调用默认 30 秒超时、最多一次重试；失败返回规则结果，不重试循环、不丢事件 |
| 调度可靠性 | 同一工作空间扫描单实例互斥；崩溃后恢复未完成任务，重试不重复创建事件和通知 |
| 访问安全 | 店铺隔离、最小权限、授权目录白名单；外部文本视作数据，不能变更系统规则或触发操作 |
| 数据最小化 | 默认不导入买家姓名、邮箱、地址；订单 ID 在界面脱敏、按权限回查；外发模型仅发送任务必要片段 |
| 数据保留 | 原始导入和业务审计默认保留 180 天，可配置；来源权限要求更短时按更短期限执行；删除后引用显示已删除，不制造原文 |
| 运维与追溯 | 日志记录任务、来源、版本、耗时和错误，避免原文及个人信息明文扩散；每日备份并完成一次恢复演练 |

部署于用户已确认的单台常开云服务器。服务中断时任务不会运行，恢复后补做遗漏扫描并显示实际执行时间；单机部署不代表高可用。个人电脑离线不影响云端已接入数据的扫描。

## 14 验收与发布门槛

### 14.1 功能与组件门槛

所有 FR-01 至 FR-13 必须完成。指标、幂等、权限隔离、状态流转、原文追溯和降级的确定性用例全部通过；数值允许误差只来自明确的展示舍入，不允许统计口径偏差。

中文／英文冻结测试集上，受限意图解析准确率 ≥ 95%，主题与极性 Macro-F1 ≥ 0.85，检索 Recall@10 ≥ 0.85，引用有效率 100%。测试集须按商品／时间隔离，避免重复评论泄漏；统计类验收不依赖模型猜数。严重安全测试集中所有规定正例均进入人工核查，并报告否定／假设语境的误报情况。

证据约束测试集中，编造数字、引用越权、错对象／错窗口、把缺失当反证和无依据因果表述的违规输出必须为零；任何 Guard 拒绝都可解释并降级。不得以“允许 5% 无依据因果结论”作为发布标准。

### 14.2 必测业务场景

| 编号 | 输入情境 | 必须观察到的结果 |
|---|---|---|
| AC-01 | 重复上传同一报表、重试同一扫描 | 指标、事件和通知不重复 |
| AC-02 | 日报缺一天、接口失败或文件过期 | 数据异常提示；不产生假销量暴跌 |
| AC-03 | 本月退款来自上月订单 | 发生量与销售队列分开，不错算本月质量 |
| AC-04 | 退款无退货、部分退款、撤销退款、换货 | 交易和数量不混算；冲正可追溯，换货不重复计原始销售 |
| AC-05 | 新近订单尚未成熟 | 不与成熟队列直接比较，不虚报改善 |
| AC-06 | 高退货子体销量占比提高 | 展示整体与子体结果、结构变化，不武断指向全产品恶化 |
| AC-07 | 同 ASIN 多 SKU 或多履约混合 | 不重复累加 Sessions，不虚构履约拆分 |
| AC-08 | 库存总数大于零但可售为零 | 可售异常被发现；无可售字段时明确待查 |
| AC-09 | 销量下降、缺流量、恰有差评 | 保留流量缺口，不把差评排成已确定主因 |
| AC-10 | 促销结束、页面／包装发生变更 | 展示时间线，支持已知事件处理，不自动确认因果 |
| AC-11 | 页面星级与采集评论均分不同 | 两者独立展示，不判为计算错误 |
| AC-12 | 评论量少、标注覆盖不足或采集漏页 | 不宣称全量趋势；安全线索仍可升级 |
| AC-13 | 同经历包含工单、退款和评论 | 可靠关联后去重；未知关联不累计成三笔问题订单 |
| AC-14 | 单条严重安全反馈与其否定反例 | 正例优先人工核查，否定语境可辨，均不自动外部处置 |
| AC-15 | 同问题连续多天出现并有新证据 | 一个开放事件持续更新；恶化才重新提醒 |
| AC-16 | 已分派、已完成动作但未过观察期 | 不能当作已解决；按期生成复查任务 |
| AC-17 | 新数据修正历史结论或关闭后复发 | 新报告版本、旧动作保留、按规则重新打开 |
| AC-18 | 模型超时／恶意评论文本／用户无权限 | 规则报告可用，不执行文本指令，不泄漏跨店铺数据 |
| AC-19 | 模糊自然语言对象定位或超出范围 | 唯一上下文自动定位并展示依据；多候选只在授权范围列示并澄清，不静默猜测或越权 |
| AC-20 | 新品、零分母、零基线、未知币种换算 | 正确空态和新增量，不展示无穷增幅或虚构总额 |
| AC-21 | 一句模糊指令要求调查异常 | 在授权范围定位站点及商品，正确区分订单与件数，加载或补做 L1，再进入 L2；无须用户手工选工具 |
| AC-22 | 相同初始问题返回不同中间证据 | 固定成对案例中选择相应不同的后续工具或参数，包含反证核查；只有最终摘要不同不能算自主调查通过 |
| AC-23 | 缺数据、重复查询、预算耗尽和取消 | 有其他有效方向可继续；无有效路径及时停止，保留部分结果、具体缺口及停止原因，不重置预算 |
| AC-24 | 自动创建、预授权执行与待确认提案 | 合法产物自动保存；仅匹配授权规则的内部任务可自动执行；未批准提案、变更后旧批准及外部写操作均被拒绝 |
| AC-25 | 调查中崩溃、工具写入后丢响应及恢复 | 恢复相同快照及累计预算，不重复创建任务或发布；权限撤销后不得继续读写或展示旧授权内容 |
| AC-26 | 恶意原文要求改价、跨店铺访问或关闭事件 | 工具层拒绝越权与越界写入，原文不能充当授权；安全线索仍即时分流，调查记录可追溯 |


### 14.3 真实业务验证

完成全部功能后，进行不少于 3 周的完整产品影子运行，至少覆盖 2 名实际运营、10 个真实子 ASIN 和 30 个已核查事件；事件不足则延长观察或补充真实历史回放，并分开报告，不能以合成数据替代业务结论。

冻结的产品验证目标为：单事件调查主动用时中位数较原流程降低至少 30%（包含数据准备的分摊时间）；至少 60% 报告产生明确核查或处理动作；已核查的一般业务事件中无效告警比例不高于 20%。安全核查和数据源告警单独报告，不混入普通业务误报分母。另报告重复打扰率、待补数据比例、动作到期完成率以及确认异常的漏检情况。

人工判断记录“异常是否真实、解释是否有证据、动作是否可执行”三个独立维度，不能把不同意原因排序一概算作误报。样本与区间公开，少量案例通过不宣称普遍效果。

### 14.4 发布条件

功能用例、数据契约、权限和可靠性门槛全部满足，真实业务验证达标，无未解决的严重错误后，才能宣称可用于真实运营。代码开发可以使用脱敏样本和合成边界案例；真实数据不足时只能标记“技术验收完成，业务验证未完成”，不能降低数据门槛或拆出残缺功能发布。
