## 2. 审查发现与执行要求

### R1 / P1：验收数据库隔离没有覆盖 Celery 队列和 beat 状态

**位置与依据：** `scripts/run_browser_acceptance.sh:62-84` 为 API、worker、beat 设置按日期分开的 PGDATABASE，但仍读取相同 `.env.local` 的 broker；worker 没有专用 queue，beat 没有独立 `--schedule`。`backend/config/settings.py:74-94` 未设置专用任务路由；`_acceptance.py` 只验证 broker 为回环地址。工作区已有 `backend/celerybeat-schedule` 及 WAL/SHM 文件。

**影响：** 当普通开发 worker 或另一环境 worker 连接同一 broker/default queue 时，可消费发给不同数据库的任务；beat 也可能复用或争用同一调度文件。此处是代码确认的隔离缺口，本次没有声称已观察到串库事故。容量运行器另用 57379 端口，不应误称其已与浏览器发生冲突。

**执行：**

1. 为验收环境建立一致的 broker/queue 命名空间；API、所有任务生产者、beat、worker、重试/派生任务都采用同一隔离策略。专用 Redis 实例/逻辑库或完整 queue 路由均可，需验证实际行为。
2. 将 beat 文件移至当前运行的 `.local/acceptance-artifacts/<run>/`，并加环境锁或等价机制，防止同一验收环境重复启动。检查存储路径是否也需按环境区分；不要仅改 worker 的 `-Q` 而遗漏生产端。
3. guard 验证数据库、队列命名空间、存储和调度文件属于同一验收环境，错误配置在种子写入前失败；输出脱敏配置，不记录密码。
4. 用两个完全隔离的临时环境模拟普通环境和验收环境，各投递可识别任务，证明消费者、任务结果和数据库归属正确。测试失败/中断也能回收本次进程；不要清空共享 Redis 或关闭用户服务。

**完成条件：** 有串队列回归证据、独立 beat 文件、启动/中断清理记录，并复跑相关浏览器流程。
