## 发布前

1. 准备 `.env.local`，只注入 `DJANGO_SECRET_KEY`、数据库/Redis 密码、`CELERY_BROKER_URL`、`DJANGO_ALLOWED_HOSTS`、`INSIGHT_STORAGE_ROOT`。真实模型密钥只在获得供应商、区域、预算批准后注入。
2. 设置 `INSIGHT_TLS_TERMINATED=1`，由前置反向代理负责 HTTPS；应用只信任已登记的 `CSRF_TRUSTED_ORIGINS`。
3. 执行：

   ```bash
   python scripts/production_preflight.py
   docker compose --env-file .env.local -f compose.v2.yml config
   docker compose --env-file .env.local -f compose.v2.yml build
   docker compose --env-file .env.local -f compose.v2.yml up -d
   ```

4. API 容器先执行迁移，再通过 `/api/v1/health/` 变为就绪；worker、beat 和 web 的健康检查必须全部通过。任一服务不健康不得开放域名。

备份必须同时包含 PostgreSQL dump、`INSIGHT_STORAGE_ROOT` 文件和 `manifest.json` 校验清单。工具会优先使用宿主机 `pg_dump`；宿主机没有 PostgreSQL 客户端时，自动通过 Compose 的 `postgres` 服务导出，并在清单记录 `database_dump_mode`：

```bash
python scripts/backup_bundle.py --output /secure/backups --compose compose.v2.yml --env-file .env.local
```

每次备份记录数据库开始时间、文件数量、SHA-256、RPO 目标和耗时。隔离恢复使用：

```bash
python scripts/verify_database_restore.py \
  --compose compose.v2.yml \
  --env-file .env.local \
  --storage-root /secure/restore/storage
```

恢复后至少核对迁移数、来源、原文件记录、评论、指标快照、报告、调查、撤回占位和审计数量。恢复演练的 `rpo_minutes`、`rto_seconds` 必须写入阶段验收记录；不能用数据库单独恢复代替联合恢复。

## 保留期清理

默认保留 180 天；来源契约的 `retention_days` 更短时优先。先预览，再执行：

```bash
cd backend
uv run python manage.py cleanup_retention --dry-run
uv run python manage.py cleanup_retention
```

清理会先写 `RetentionTombstone`，再删除原始文件内容并保留校验值、来源批次和审计占位。被报告、语义 claim 或调查引用的事实不会物理删除；评论/售后检索索引可重建，旧索引只清空索引字段。下载已清理原文件会返回 410，提示通过批次和校验值追溯。

python scripts/capacity_probe.py --dry-run

## 回退与值守

- 应用回退：保留上一份镜像和迁移版本；先停止新 worker，再确认没有运行中的领域命令，回退 API/web，最后恢复 worker/beat。
- 安全停栈命令（保留持久卷）：`docker compose --env-file .env.local -f compose.v2.yml stop worker beat api web`；确认数据库仍需运行后再选择 `docker compose ... stop`。`down` 默认不删 named volumes；禁止用 `down -v` 作为生产回退。
- 镜像回退要先取得上一版本 API/worker/beat/web 的 registry digest 并核对对应迁移兼容性，再将上一 digest 配置为部署镜像并启动；本机没有已签收的生产旧版 digest，本步骤未执行，不能用当前 `latest` 冒充回退版本。
- 数据回退：优先恢复到隔离数据库核对，不直接覆盖生产库；需要切换时记录 RPO、RTO、备份 manifest 和审批人。
- 告警优先级：安全线索、来源权限撤销、数据库不可用、Redis 不可用、outbox 长时间积压、保留清理失败。
- 任何外部 Amazon/ERP 变更都只能由人工根据提案 payload hash 和交接编号执行，系统没有外部写接口。

## 最终放行

生产健康、联合恢复、保留期、容量、全流程 E2E、三周影子运行和业务负责人签收全部有记录，且 P0 缺口为零，才可将 S7 标记为完成。真实报表、真实模型、真实服务器和运营签收缺失时，代码状态保持“可验收”，不写成“已通过”。
