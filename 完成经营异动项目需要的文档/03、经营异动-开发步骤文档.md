## 0. 怎样使用这三份文档

先从 PRD 明确问题、口径、权限与验收；再从 TDD 找到决策依据、边界、代码和数据流；最后按本文逐阶段核对输入、实现、证据和退出条件。开发阶段不等于分产品版本，完整产品保留 FR-01—13、AC-01—26；当前内部演示与后续正式上线按 PRD 2.4 分别签收。

参考探渊Markdown的“分阶段输入/实现/验收”“工具签名”“ADR与故障排查”组织方式；不照搬其多Agent、全网搜索、任意数据库查询或先备齐全部外部服务的前提。本项目按实际授权、工具白名单、源码差异和两阶段完成标准组织。

当前项目已有大量实现。执行时先做“已有/缺失/冲突/未验证”差异审查，复用已满足契约的代码，再补缺。不要照探渊的从零脚本删除重建当前工程，也不要把测试文件存在当通过。

### 0.1 本次交付的事实

本次修订这三份 Markdown，阅读了项目需求、主线代码、测试入口、部署文件与历史记录；未执行后台任务、全量测试、收费调用、部署或业务验证。最新模型质量入口仍保留未确认达标的状态。下面所有“通过”均是阶段退出条件，不是本次运行结果。

### 0.2 每项技术表述的证据等级

| 等级 | 能证明什么 | 合适表达 |
| --- | --- | --- |
| D：设计 | 有方案、约束和理由 | “设计采用……，需要验证……” |

### 1.2 隔离验收环境

数据库、文件目录、Celery namespace、Beat 文件、端口和账号同时隔离，不能只换数据库。先确认验收脚本版本和当前端口占用；不用生产数据库执行 seed 或故障注入。

已有浏览器验收 runner 可同时准备数据和启动自有 API/worker/前端。以下为**需执行时使用的合成验收示例**，不是本次已经启动：

```bash

ACCEPTANCE_ACCOUNTS_FILE=.local/acceptance-accounts-docs-20261015-v1.json \
ACCEPTANCE_RUN_VERSION=1 \
bash scripts/run_browser_acceptance.sh 2026-10-15
```

runner 使用隔离命名和自有进程清理，日期用于合成 fixture 回放，不代表真实业务日期。已有同名环境时先审查复用/新版本策略；不得删除未知锁或杀占用端口的他人进程。账号文件仅本机保存，截图隐藏敏感数据。此 runner 也不等同于完整模型质量/真实业务验收。

下文命令均从 `backend/` 目录执行，使用 `pytest-v2.ini`。需先具备本机 PostgreSQL、隔离测试配置和 `.env.local`；`PGDATABASE` 指向隔离验收基库，pytest 创建其测试数据库。先确认数据库用户权限和当前 test database 策略，不使用生产库或盲目 `--reuse-db`。

每个阶段示例中的 `pytest ...` 是上述命令最后两行的替换项，保留相同隔离和默认离线设置。真实供应商测试另走已绑定授权的候选流程；测试内的 mock 不能冒充真实供应商验证。

一次改动只提交本阶段明确文件；当前工作区存在大量既有修改，禁止 `git add .` 把无关工作一并提交。无需为文档写作创建发布或模型调用授权。

## 3. D0—D3：先保证事实与计算正确

**退出：** 全部 13 个 FR、26 个 AC 有去向；当前实现和目标冲突可定位；没有把历史原型验收继承为当前通过。

### 9.2 把检索未命中当成反证（设计风险）

- **现象：** 未找到过热原文就认为商品没有过热问题，或用“外观满意”反驳电气故障。
- **根因：** 混淆相关命中、范围上下文、检索覆盖与事实否定，且反证未约束同主题。
- **处理：** 相关/上下文结果分层，返回完整性；反证匹配主题、对象、时间和实际/否定/假设语境；未命中保持未知。
- **验证：** 无答案、漏召回、同主题否定、不同主题好评和冲突案例逐项测。

### 9.3 写后崩溃重放（故障注入场景，非生产事故）

- **故障窗口：** 业务命令提交成功，但节点/checkpoint 尚未保存，重放可能再次执行写入。
- **处理：** run+logical_action_id 的命令回执、领域幂等、租约与当前授权；重放先查回执。
- **验证：** 在“提交后/记录进度前”注入故障，查实际任务数、回执、步骤与预算；旧 Worker 写入被拒。
- **边界：** 不声称消息 exactly-once；已提交合法写入取消后仍保留。

### 9.4 预算与整轮停止（历史执行记录）

## 11. 面试表达模板

### 11.1 90 秒项目介绍

> 我做的是面向亚马逊商品运营的经营异动分析项目。运营看到销量下降或退款增加后，需要在多张报表和评论间核查，常见问题是统计口径错位、结论没有可回查证据，以及处理后没有复查。
>
> 项目按事实接入、确定性计算、事件分诊、证据调查、处理复查来组织。后端主线用 Django、PostgreSQL 和 Celery，前端用 React。标准检查用固定流程，复杂调查用一个有界 LangGraph Agent；模型选择受限工具，数值、对象范围、引用和写入权限由服务端控制。
>
> 重点难点是区分退款发生与成熟队列、绑定来源版本、以及崩溃恢复后不重复花费或重复创建任务。项目保存调用账本、检查点和命令回执，并用成对中间证据验证调查路径是否随证据变化。
>
> 目前可展示主线源码、专项验证和真实模型失败修复记录。完整智能质量、独立裁决和业务收益仍按门槛核验，我不会把合成样本或设计目标当成生产效果。

按实际情况替换“我做”的具体范围；若并未亲自实现某模块，表述为负责设计、参与排查或正在补齐，不能直接认领全部代码。

### 11.2 五分钟展开顺序

1. 业务痛点及一个真实或明确标合成的事件（约 45 秒）。

3. 架构与 L0/L1/L2 分工、选型取舍（约 60 秒）。
4. 选一个自己实际处理的难点，展示日志/代码/验证（约 90 秒）。
5. 评测、性能与业务价值的实际证据及当前限制（约 45 秒）。

- 设计并实现商品经营异常分析链路，覆盖报表接入、版本化事实、指标检测、证据报告与内部处理复查。
